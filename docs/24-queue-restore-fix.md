# 24 · 重开 App 后播放列表不同步：三个真因

用户第三次反馈同一件事，所以这次不再"再补一点"，而是把存/读两端全部核对了一遍。
查出**三个各自独立**的原因，任何一个都会让列表丢失：

## 原因 1：音乐库和电台根本不存快照

| 路径 | 有没有存 `PlaybackSession` |
|---|---|
| NAS 浏览 | ✅ 存了 |
| 音乐库 | ❌ **没存**（只记了"最近播放"） |
| 网络电台 | ❌ **没存** |

只有 NAS 会写快照，所以从音乐库/电台推的列表重开必丢。已补齐（单曲也存一条）。

## 原因 2：音乐库存快照用的键是 SSID

`LibraryViewModel` 存盘键原来写的是 `deviceLabel`（就是 `DOSS DS-1831_ADB4` 这种 SSID），
而恢复时按 `uuid` / `ip:` 找 —— **存的键和读的键不是同一个**，即使存了也永远读不到。

已改为统一走 `PlaybackKey.of(deviceUuid, deviceIp)`，并把 `deviceUuid` 从
`MainActivity` 一路传进 `LibraryViewModel` / `RadioViewModel`。

## 原因 3：恢复只看本地快照，不看设备

列表其实在设备上（`plicount` / `plicurr`），而恢复逻辑只读本地快照。
于是出现"设备明明在放第 3 首，界面一片空白"。

现在判定逻辑收敛成一个纯函数 `QueueRestore.plan(snapshot, device)`：

| 设备队列 | 本地快照 | 结果 |
|---|---|---|
| 有，且长度一致 | 有 | 用快照标题 + 设备位置（`(offset + plicurr-1) % size`） |
| 有，但没有/长度不符 | 无/不符 | **造占位列表**（长度取设备值），至少能看到"设备上有 N 首、第 i 首" |
| 无 | 有 | 展示上次快照，并注明"设备当前没有队列" |
| 无 | 无 | 空状态（如实） |

三个细节：

- **旋转偏移要持久化**：设备只认 `playlist` 的 `index=0`，下发前我们把列表旋转过，
  所以 `PlaybackSession` 新增 `deviceOffset` 字段（老快照缺字段按 0 读，兼容）。
- **占位项不能投流**：`device://track/N` 这种假地址点了会发 `next`/`prev` 按设备跳位，
  并且不给删除按钮（设备侧列表我们改不了）。
- **恢复时机搬到启动**：`ConsoleViewModel.restoreLastQueue()` 在 App 启动时跑，
  不再等用户点开播放页 —— 否则"重开列表空着"看起来就像恢复失效。

## 真机验证（`.153`）

按 App 的实际做法跑了一遍：5 首、从第 3 首起（旋转后 `index=0` 下发）。

```
推送后:     plicount=5 plicurr=1 status=play
停掉 m3u 服务（≈ App 被杀）后重新读:
            plicount=5 plicurr=1 → 映射得本地第 3 首，预期第 3 首 ✓
```

## 单测

- `QueueRestoreTest` **10 个**：长度一致 / 旋转偏移 / 回绕 / 无快照占位 / 长度不符 / 只有快照 /
  都读不到 / 设备读不到但快照在 / 占位标题 / 设备位置越界
- `PlaybackSessionTest` **5 个**：编解码往返（含 `deviceOffset`）/ 老快照缺字段 / 索引夹取 / 坏数据 / `remaining`
- 全量 **359 用例 0 失败**
