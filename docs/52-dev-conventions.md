# 52 · 开发约定（每次动手前先看这一页）

> 这些不是建议，是这个项目的硬规则。违反过的地方都留了记录，别再犯一遍。

---

## 一、诊断台必须跟着功能一起长（2026-11-04 用户明确要求）

> 「诊断台模块应该跟随开发的进展实时跟进，这是继续开发的基础，
> 后续任何开发动作必须伴随诊断台进化」

### 这条规则在防什么

这个项目**没有真机自动化测试**。所有验证靠两样东西：
1. 单元测试（只能覆盖纯逻辑，碰不到网络、碰不到设备、碰不到界面）
2. **用户截图给我的诊断报告**

所以诊断台是唯一的"眼睛"。它的盲区 = 我看不见的地方 = 只能靠猜的地方。

而**每加一个新功能，就多一块盲区**。上一轮刚做的"统一遥控口令"层就是活例子：
口令发出去是什么、成没成功、为什么失败、花了几毫秒 —— 全是黑盒。
真出问题时，用户只能说"点了没反应"，我只能猜。

### 具体怎么做（每次加功能必须走完）

新增任何**有状态**或**会失败**的东西时，同一批改动里必须包含：

**1. 注册一段诊断**（如果它有自己的状态）

```kotlin
AppDiagnostics.sections.register(
    "指令",                       // 唯一 id
    "指令",                       // 报告里的标题
    { if (最近有失败) Severity.WARN else Severity.INFO },   // 级别是函数
) {
    buildString {
        appendLine("  最近一条：${最近指令}")
        appendLine("  结果=${最近结果}")
    }
}
```

**2. 失败路径必须记一条**（`Severity.ERROR` / `WARN`）

```kotlin
AppDiagnostics.log.record(DiagnosticEntry.ofError(now, "动作名", error))
```

**3. 成功路径也要记**（`Severity.INFO`，带耗时）

只有失败才记的话，**"没反应"和"根本没触发"分不开** —— 这两种的修法完全不同。
用 `log.timed("动作名") { ... }` 一次搞定。

**4. 动作名必须是"用户做了什么"**

`playQueueItem` / `probeSaved` / `volumeKey` —— 用户说的是"点播放没反应"，
标签要对得上这句话。写类名（`ConsoleViewModel`）等于把行号换了个地方写。
CI 有 `scripts/check-diagnostics-labels.py` 挡着。

### 判断"这块要不要加诊断"

问三个问题，任一答"是"就必须加：

1. 它会**发网络请求**吗？（会 → 要知道成功/失败/耗时）
2. 它会**静默失败**吗？（会 → 必须留痕，否则用户只看到"没反应"）
3. 它的状态**用户会问"为什么"**吗？（会 → 报告里要有）

### 报告要能回答的问题

一份好的诊断报告，用户截图给我之后，我应该**不用再问任何问题**就能定位。

现在的报告已经能回答：崩在哪、几台设备在线、哪条取数通道没通、队列归属谁、
后台服务跑没跑、问题按严重度分了几条。

**还没覆盖的（下次开发要补）**：
- 遥控口令层（发什么、成没成、为什么失败、耗时）
- 电台（加了不响是为什么）
- 在线曲库（tt-music 搜不到是为什么）
- NAS / 本地曲库
- 悬浮窗 / 语音

## 二、其他一直在守的规则

### 交付流程（每个功能一个 PR）

```
feature 分支 → gh pr create → 等 CI 绿 → squash merge → main 上再验一遍 CI → 下载 APK 核对
```

APK 核对三件事：包名/版本号、签名指纹（`dc3f1f24…`）、应用名（声控台）。

### 诚实优先

- **实测通过 / 实测打脸 / 未确证** 三种情况分开写，不混
- 「命令回 OK」≠「功能生效」。这条被坑过至少四次：
  `chext=0` vs `1`、`resume` 回 OK 但 status 仍 stop、https 电台回 OK 但没播、
  改名回 OK 但被 SSID 覆盖回去
- 单测全绿 ≠ 功能可用。单测只证明"逻辑自洽"，不证明"设备认"

### 删代码前先归档

要删的功能，先把**完整源码 + 为什么删 + 怎么恢复**写进 `docs/archive/`，
再删。已经有：`docs/archive/legacy-multiroom-slaves.md`。

### 一致性靠「单一入口 + 编译期强制」

不靠文档、不靠自觉。具体手法：
- `private constructor` + 唯一工厂方法（`SavedDevice.of`）
- `internal` 限制可见性（`LinkPlayTransport.encode`）
- 必填参数（`safeLaunch(source)`、`QueueBus.begin(deviceIp, …)`）
- CI 静态检查（`check-init-order.py`、`check-diagnostics-labels.py`）

拆模块只是把规则物理强制得更彻底，**不产生一致性本身**。

### 不做的事

- 不逆向商业 App 取流、不复用原厂凭据、不绕过付费
- 不抄 GPL/AGPL 代码（抄设计可以）
- 不给"按了没反应"的按钮（能力位决定渲染）
- 不假装成功（失败要如实说，不能只说"失败"）

## 三、每次动手前的自检清单

```
□ 这块会发请求 / 会静默失败 / 用户会问为什么 吗？→ 是则加诊断
□ 诊断标签是「用户做了什么」还是类名？→ 必须是前者
□ 新增的入口有没有被能力位控制？→ 没有的话，不支持时会变成假按钮
□ 失败原因能翻译成人话吗？→ 不能的话用户看不懂
□ 改完的单测数量是增还是减？→ 减了要说清为什么
□ 有没有真机验证？没有的话交付时要标明"未验证"
```
