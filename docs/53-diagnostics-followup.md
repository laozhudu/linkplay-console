# 53 · 诊断台跟上开发：第一个盲区补完了

> 起因：用户 2026-11-04 提出「诊断台模块应该跟随开发的进展实时跟进，
> 这是继续开发的基础，后续任何开发动作必须伴随诊断台进化」

这条要求先落成了规则（`docs/52`），这一轮做第一个示范。

---

## 一、为什么这条要求是对的

这个项目**没有真机自动化测试**。验证只有两条路：

1. 单元测试 —— 只能覆盖纯逻辑，碰不到网络、碰不到设备、碰不到界面
2. **用户截图给我的诊断报告**

所以诊断台是唯一的眼睛。它的盲区 = 我看不见的地方 = 只能靠猜的地方。

而**每加一个新功能就多一块盲区**。上一轮做的「统一口令层」就是活例子：
口令发出去是什么、成没成功、为什么失败、花了几毫秒 —— 全是黑盒。
真出问题时，用户只能说「点了没反应」，我只能猜。

---

## 二、这一轮补的：口令流水

### 三种情况，界面上长得一模一样

| 真实情况 | 用户看到 |
|---|---|
| 发了，设备没照做（`chext` 那种） | 点了，没反应 |
| 根本没发（设备睡了 / IP 变了） | 点了，没反应 |
| 发了，回包看不懂 | 点了，没反应 |

**三种的修法完全相反**：第一种查协议，第二种查网络/地址，第三种查固件差异。
不记录的话只能靠猜。

### 做法

`CommandTrace`（纯 JVM，40 条环形）记在**传输层**，不是调用方：

```kotlin
class LinkPlayTransport(
    private val client: DeviceHttpClient,
    private val trace: CommandTrace = CommandTrace.DEFAULT,
    private val clock: () -> Long = { System.currentTimeMillis() },
) : RemoteTransport {
    override suspend fun dispatch(ip: String, command: RemoteCommand): DispatchResult {
        val started = clock()
        val result = /* … 真正下发 … */
        trace.record(Entry(started, labelOf(command), ip, result.isAcked, failureText, clock() - started))
        return result
    }
}
```

**为什么收在传输层**：每一次下发都要记，放在调用方就必然有人漏
（本项目 16 个调用点）。收在一处才是单一入口。

### 报告里长这样

```
[指令]
  共 47 条 · 成功 44 · 失败 3 · 平均 68ms
  最近 6 条（新→旧）：
    03:14:22  SetVolume(45) @192.168.99.164 → OK  72ms
    03:14:20  Pause @192.168.99.164 → 失败：设备里没有可播放的内容  45ms
    03:14:18  Play @192.168.99.164 → OK  61ms
```

**连续失败 ≥ 3 次会单独标出来**：

```
⚠ 连续失败 3 次 —— 可能是设备离线或地址变了
```

理由：连续失败 = **整条链路断了**，和「偶发一条失败」是两回事。
前者查网络，后者查协议。混在一起看会误判。

### 四个设计决定

| 决定 | 为什么 |
|---|---|
| **成功也记** | 只记失败的话，「没反应」和「根本没触发」分不开 |
| **记设备 IP** | 多台设备时才知道发给了谁（`.153` / `.164` / `.181` 都出现过） |
| **记耗时** | 区分「慢」和「断」。69ms 和 5000ms 是不同问题 |
| **记人话不记协议** | `SetVolume(45)` 不是 `setPlayerCmd:vol:45`；`失败：设备没有响应` 不是 `Unreachable` |

### 诊断段的级别是动态的

```kotlin
AppDiagnostics.sections.register(
    "commands", "指令",
    {
        when {
            trace.consecutiveFailures() >= 3 -> Severity.ERROR   // 链路断了
            trace.failedCount > 0 -> Severity.WARN              // 有失败但还能用
            else -> Severity.INFO
        }
    },
) { trace.render() }
```

这样报告头的汇总（`E1 W2 I5`）会直接反映口令层的健康状况，
不用翻到下面才知道「哪一块在喊」。

## 三、验证

| 项 | 结果 |
|---|---|
| `:core-protocol:test` | 611 用例 0 失败（+14） |
| `:core-diagnostics:test` | 41 用例 0 失败 |
| `:app:testDebugUnitTest` | 47 用例 0 失败 |
| 合计 | **699 用例 0 失败** |
| `assembleDebug` | 成功 |
| 两个 CI 脚本 | 通过 |

`CommandTraceTest` 14 个，锁的是「能不能分清三种情况」：

- 空流水说「还没有下发过指令」，不说「平均 0ms」（0 条时报平均是误导）
- 成功和失败分开计数
- 失败原因带进报告
- 成功条目也保留（否则分不清「没反应」和「没触发」）
- 设备 IP 显示出来（多设备时能定位）
- 连续 3 次失败才叫「链路断了」，2 次不算（可能是正好在切输入源）
- 一次成功会打断连续失败计数
- 环形容量不截断总计数
- 指令名是人话不是类名（`Play` 不是 `io.github...RemoteCommand$Play`）

**未验证**：真机上点按钮后诊断页是否真的出现这一段（`.153` 离线，`.164` 只读核对）。

## 四、还欠的盲区（按优先级）

| 盲区 | 现在能看到什么 | 缺什么 |
|---|---|---|
| **电台** | 什么都没有 | 加了链接不响是为什么（scheme / 编码 / 设备不认 https） |
| **在线曲库** | 什么都没有 | tt-music 搜不到是为什么（服务端空库 / 网络 / 认证） |
| **NAS** | 什么都没有 | DLNA 列不出内容是为什么 |
| **本地曲库** | 什么都没有 | 扫不到歌是为什么（权限 / MediaStore） |
| **悬浮窗** | 只有「服务跑没跑」 | 权限被拒？布局算错？被系统杀了？ |
| **语音** | 什么都没有 | 识别错 / 意图没匹配上 / 匹配上了但没执行 |
| **配网** | 什么都没有 | AP 扫描空？连接超时？连上了但拿不到 IP？ |

**下一个功能做到哪，就顺手把那一块的诊断补上。** 不要再攒到最后。
