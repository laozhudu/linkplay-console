## 二、三个关键发现

### 发现 1 · `MediaProvider` 接口写了，但只有 1 个实现，调用方还绕过它

`core-protocol/mediasource/MediaProvider.kt` 的设计**正是你想要的东西**，
注释里写得明明白白：

> 把「取列表」和「取直链」抽出来之后，**加源 = 加一个实现类**，
> 播放链路（PlayQueue / m3u / RelayMediaServer）一行不动。

但实际状况：

```
实现了 MediaProvider 的：SubsonicClient（只有 1 个）
OnlineViewModel 怎么用的：import io.github...SubsonicClient  ← 直接依赖具体类，不走接口
```

**这是这个项目第三次出现同一个病**：

| 第几次 | 抽象 | 症状 |
|---|---|---|
| 1 | `MediaProvider` | 接口写了，app 层 0 处消费（docs/43） |
| 2 | `DeviceCapabilities` | 能力表算出来被 `_` 丢弃（docs/51） |
| 3 | `MediaProvider` 又一遍 | 唯一实现者存在，但调用方绕过接口直接依赖具体类 |

根因是同一个：**抽象写了，装配没做**。

### 发现 2 · 「唯一整单下发入口」只覆盖 2/5 个源

`startQueueOnDevice` 的注释写着"全 App 唯一入口"，实际调用点：

```
LibraryViewModel:360   ✅
OnlineViewModel:193    ✅
（NAS / 电台 / 播放队列 —— 都不走这里）
```

所以那句话是**声明，不是事实**。NAS 自己实现了 `ClientSideQueue` 降级链，
电台直接发 `playUrl` 命令，播放队列直接发 `PlayQueue` 请求。

**同一个动作有三份实现，改一处必然漏两处。**

### 发现 3 · 真正的"播放器"是投送层，不是界面

从「用户点一首歌」到「音箱出声」，中间这层现在散在这些文件里：

| 文件 | 行数 | 干什么 |
|---|---|---|
| `QueueStarter` | 115 | 整单下发 + 三段降级（PlayQueue → m3u → 逐首） |
| `DeviceQueuePush` | 106 | 推队列到设备 |
| `DevicePlaylistGateway` | 128 | 歌单相关的设备交互 |
| `QueuePlaybackService` | 304 | 后台服务（App 退出后继续控制） |
| `RelayMediaServer` + `LocalMediaServer` | ~500 | 手机当服务器（https 转发 / 本地文件） |

**650～1100 行**，这才是"播放器"的核心。

它决定三件事：
1. 走 PlayQueue 还是 m3u 还是单曲直投
2. 本地文件怎么变成设备能拉的 URL
3. https 的源怎么转发（音箱不认 https）

## 三、判断

### 内容源各自独立 —— ✅ 完全合理

**但"独立"的含义要定清楚：拆成实现类，不是拆成 Gradle 模块。**

| 做法 | 收益 | 代价 |
|---|---|---|
| 5 个 Gradle 模块 | 物理隔离 | 5 份 build.gradle、编译变慢、依赖图要维护 |
| **5 个实现类 + 1 个接口 + 注册表** | **加源不改别处** | 几乎没有 |

关键在于：这 5 个源之间**没有依赖关系**（NAS 不需要知道电台）。
而"加源不改别处"这个收益，**用接口就能达到，不需要 Gradle 模块**。

对比：`core-protocol` 8637 行都没拆，因为它是一个整体（协议层互相依赖）。
内容源天然独立，所以可以拆 —— 但拆到"包 + 接口"就够了。

**什么时候才该升格成 Gradle 模块**：某个源开始有**独立第三方依赖**时
（接 WebDAV 要库、接加密音源要解密库）。那时拆才有意义。

### 播放器独立 —— ⚠️ 需要修正：拆成三个东西

「播放器」这个词在这个项目里指三件不同的事：

| | 是什么 | 现状 | 该放哪 |
|---|---|---|---|
| 播放**控制** | 发 play/pause/音量给音箱 | 已做（`RemoteCommand`） | 遥控侧，不动 |
| 播放**页** | 842 行的 `PlayerScreen` | 已做 | 界面侧 |
| 播放**投送** | 把 URL 变成设备能播的东西 | **散在 4 个文件** | **← 这才是该独立的** |
| 播放**引擎** | 手机自己出声（Media3） | 还没做 | 未来独立 |

**混在一起的后果**：
- 本地播放要依赖遥控命令定义（不合理）
- 或者遥控层被塞进 Media3 —— **这个更致命**：协议层现在是纯 JVM 零依赖，
  710 个测试跑得快；塞进 Media3 就得跑模拟器

**你说的"播放器"最可能是「投送」这一层**，因为它才是"内容 → 声音"的转换器。

## 四、建议结构

```
内容源    media-source           MediaProvider 接口 + MediaTrack + 注册表
          ├─ source-local        手机本地（MediaStore）
          ├─ source-nas          NAS / DLNA
          ├─ source-subsonic     在线曲库
          └─ source-radio        电台
                │ 只产出「可解析的曲目」
                ▼
投送层    media-delivery         整单下发 + 降级链 + 中继服务器
          （← 你说的"播放器"，650～1100 行收进来）
                │ 只接受「URL 列表 + 设备能力」
                ▼
遥控层    core-remote            已做（语义指令 + 能力位）
                
播放引擎  core-player            本地出声（Media3）+ PlaybackRoute   ← 未来
```

### 三条可验证判据

模块化不模块化，看这三条能不能做到：

| 场景 | 目标 |
|---|---|
| 加一个新内容源（WebDAV / 网易云） | 只加**一个实现类 + 注册一行**，投送链路 0 行改动 |
| 加一个新设备类型（电视） | 只改**能力表**，内容源 0 行改动 |
| 加本地播放 | 只加 `PlaybackRoute.Local`，内容源和投送 0 行改动 |

做不到这三条，模块划分就是假的 —— 只是把代码挪了目录。

## 五、执行顺序（我的建议）

### 第一步：让 `MediaProvider` 真正被用起来（小改动，收益最大）

这是**唯一现在就该做的**，因为：
- 接口已经存在且设计正确
- 5 个源里已经有 1 个实现了
- 剩下 4 个实现它是机械工作
- 做完之后判据 1 成立

具体：
1. NAS / 本地 / 电台 / 播放队列 各实现一个 `MediaProvider`
2. `OnlineViewModel` 改成依赖接口而不是 `SubsonicClient`
3. 加一个注册表（谁是当前可用源、谁配置好了）
4. `startQueueOnDevice` 改成只接受 `MediaProvider` 的输出

**风险**：NAS 和电台现在各有自己的降级链，收进统一入口时**行为可能变**。
所以这一步要**先补诊断**（见下），再动。

### 第二步：把投送层收成一个包

现在散在 `playback/` 里的 4 个文件 + 2 个 server，收进 `delivery/`，
对外只暴露一个入口：

```kotlin
suspend fun deliver(tracks: List<ResolvedTrack>, device: RemoteTarget): DeliveryResult
```

## 六、按规则：这一步必须伴随诊断进化

用户的硬规则：**任何开发动作必须伴随诊断台进化**。

内容源这块正好是七个盲区里的四个（NAS / 在线曲库 / 本地曲库 / 电台）。

每个源都要注册一段诊断：

```
[内容源]
  subsonic  已配置  最近搜索 12 条 / 38ms
  nas       已配置  最近列目录 1931 首 / 210ms
  local     已配置  最近扫描 0 首  ← 可能没权限
  radio     已配置  库内 24 个台
```

要回答的问题：
1. 这个源**配置好没有**（没配的不该出现在可选项里）
2. 最近一次**取数据成功没有**、多少条、耗时多少
3. 失败时**为什么**（连不上 / 认证失败 / 空库 / 格式不支持）

**注意最后一条**：`local 最近扫描 0 首` 和 `local 没权限` 是两回事，
诊断要说清楚是哪种。

## 七、结论

| 你的判断 | 我的评价 |
|---|---|
| 内容源各自独立拆分 | ✅ **对**，但拆实现类不拆 Gradle 模块 |
| 播放器独立一个模块 | ⚠️ **对一半** —— 该独立的是「投送层」，不是界面 |
| 内容来源多方面 | ✅ 已经是事实（5 个源），问题是五套各写各的 |

**最关键的一条**：这个项目已经三次"抽象写了没装配"。
所以这次不要先建模块骨架，而是**先把 `MediaProvider` 真的接上 5 个源**，
让"加源不改别处"这件事在代码里成立，再谈模块边界。

顺序：**接接口 → 补诊断 → 收投送层 → （未来）本地播放**。
