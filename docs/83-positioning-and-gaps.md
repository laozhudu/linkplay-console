## 零、定位（一句话）

> **私人音频中枢遥控器** —— 把 NAS、在线曲库、电台里的声音送到我家那几台音箱上，
> 顺手控一下电视和空调。**只给我一个人用。**

三个关键词各自排除了什么：

| 关键词 | 排除了 |
|---|---|
| **私人** | 不做多用户、不做分享、不做 publish 给别人用、不需要「陌生人也能配得通」 |
| **音频** | 红外/蓝牙是**顺手扩展**，不是主线；不做视频投屏、不做游戏 |
| **中枢遥控器** | 不做音乐库管理（NAS/Navidrome 的事）、不做转码服务器（tt-music 的事） |

**为什么是这个定位，而不是 docs/49 说的「多协议遥控平台」**：
「多协议遥控平台」是个**产品级野心** —— 要覆盖别人家的设备、要泛化、要能发布。
你自用不需要那些。而且实测数据说明这条路走不通（见第二节的缺口 A1）。

## 二、定位漂移了三次

| 阶段 | 当时定位 | 触发的文档 |
|---|---|---|
| **1** | DOSS 音箱的现代重写版遥控器 | 起点（逆向 990803.apk） |
| **2** | 遥控器 + 自己的检索层（内容外部提供） | `docs/57`，当时选 B |
| **3** | **多协议遥控平台**（WiFi/蓝牙/红外/本地播放） | `docs/49` |

第 3 次漂移是最大的问题：它把「顺手扩展」写成了「平台」。

**证据**：`docs/49` 的表格里，红外/蓝牙和 WiFi 并列成「三种传输」，看起来同等重要。
但实际使用频率完全不是 —— 你天天用音箱，一年用几次红外？

**判断**：第 3 次漂移是「因为能做，所以要做」，不是「因为要用」。

## 三、这个定位下，什么最重要

按「你每天会做的动作」排：

| 动作 | 频率 | 现在能不能一步完成 |
|---|---|---|
| 想听歌 → 找歌 → 音箱响 | **每天** | ❌ **要跨 3 个页面、先决定去哪个源搜** |
| 换一台音箱放 | 每周 | ✅ 有（切换设备） |
| 三台成组同步 | 偶尔 | ✅ 有（勾选式组网） |
| 睡前定时关 | 偶尔 | ✅ 有（SleepTimer 预设） |
| 调音量 | 每天 | ✅ 有 |
| 控电视/空调 | 一年几次 | ⚠️ 红外刚做第一步 |
| 在手机上直接放（不投音箱） | 偶尔 | ✅ 有（Media3 已接） |

**结论：唯一「每天都要做但做不到一步」的动作，是「找歌」。**

这就是定位下最该补的东西 —— 不是新模块，是**入口**。

## 四、缺什么模块：缺的不是模块，是三个「串联件」

8 个模块已经够多了。真正的缺口是「没有一个东西把 8 个模块串成用户的一个动作」。

### A 类 · 功能缺口（定位需要，现在结构上做不到）

#### A1 · 统一搜索 —— **最大的缺口**

**现状**（实测代码）：

| 源 | 怎么进 | 入口 |
|---|---|---|
| 洛雪（在线曲库） | `LxSearchScreen` 搜歌 → 取直链 → 投送 | 一级 Tab |
| 电台 | `RadioScreen` 搜台 → 播放 | 媒体库 → 电台 |
| NAS | `NasScreen` 走 DLNA 浏览目录 | 媒体库 → NAS |
| 本地 | `LibraryScreen` / `MyMusicScreen` | 媒体库 |

**四个源，四套搜索，四个入口。** 用户想「放首歌」得先想「这首歌在哪个源」。

这是定位的核心动作，却是断的。

**而且已经有证据证明它是核心动作** —— `Nav.kt:15` 的注释原文：

> 洛雪音乐 —— 一级页面，不藏在"媒体库 → 其它入口"里。
> 理由就是用户的抱怨：搜一首歌要"进媒体库 → 其它入口 → 洛雪 → 搜 → 点"，
> **五次操作**。一级入口之后是"点洛雪 → 搜 → 点"，而且搜完还能直接切播放页。

现在底部是 **4 个 Tab**（设备 / 播放 / 洛雪 / 媒体库）。
洛雪被提成一级页，说明「找歌」确实是主路径 —— 但**只解决了「洛雪这个源」的入口，
电台/NAS/本地还是散在媒体库里**。

**为什么不能简单加个搜索框**：四个源的搜索能力完全不同 ——
洛雪能按歌名搜、电台只能按台名/国家搜、NAS 只能浏览目录（DLNA 的 ContentDirectory 有 Search 但很多服务器不支持）、本地是 MediaStore。

**建议**：不是「统一搜索」，是**「一个输入框 + 分流」**：
输入后并发问四个源，各自返回「我找到几条」，用户点哪个源看哪个。
**不做结果合并排序** —— 跨源的排序没有意义（NAS 的《晴天》和网易云的《晴天》不是一回事）。

成本估计：一个 `SearchHub`（app 层，约 200 行）+ 四个源的适配（各 30 行）+ 一个页面。
**不需要新 Gradle 模块**，因为它是纯编排，没有第三方依赖。

#### A2 · 跨源队列 —— **结构上做不到**

**证据**（`core-protocol/.../queue/ClientSideQueue.kt:4`）：

```kotlin
data class QueueItem(
    val url: String,
    val title: String,
    val artist: String? = null,
    val album: String? = null,
    val durationSec: Long = 0,
    val mimeType: String = "audio/mpeg",
    val albumArtUrl: String? = null,
)
```

**没有 `source` 字段。** 所以队列表达不了「这首来自 NAS，那首来自洛雪」。

现在的实际行为：每个源各自 `startQueueOnDevice`，一次投一个源的列表。
想把「NAS 一首 + 洛雪一首」放一个队列 —— 做不到。

**值不值得做**：看你的使用习惯。如果「按专辑听」就够，不用做；如果会「攒一个混合歌单」，那要加 `source` 字段 + 每首在播放前解析直链（洛雪的直链有时效，必须临播前取）。

**成本**：加字段是 1 行，但「临播前解析」会动到队列执行器 —— 中等改动，风险在队列。

#### A3 · 本地 ↔ 设备 接续播放 —— **是「切换」不是「搬过去」**

**证据**（`app/.../playback/PlaybackRouter.kt`）：

```kotlin
enum class PlaybackOutput { Remote, Local }
```

`PlaybackRouter` 是**选一个输出**，不是**把播放搬过去**。
`PlaybackViewModel:170` 的「切换到另一台设备」是设备↔设备，也不是手机↔设备。

`docs/77` 建议的 `PlayerTransferState`（搬 8 个字段：位置/队列/播放态/循环/随机…）**没有落地**。

**场景**：你在手机上听着歌出门/进卧室，想「让它接着在音箱上放」。现在要重新找歌、重新投。
**成本**：中等（`PlayerTransferState` 那套是现成的，但要处理「本地队列 → 设备队列」的投影）。

### B 类 · 质量缺口（有，但不达标）

#### B1 · `core-discovery` 252 行 0 个测试

```
core-discovery   1 文件   252 行   0 测试
```

**8 个模块里唯一一个零测试的。** 它是 SSDP 设备发现 —— 项目最底层的能力之一，
现在改一行只能靠真机试。

#### B2 · MediaSession 没接 —— 通知栏/耳机键/锁屏都没有

**证据**（`app/.../playback/local/LocalPlayer.kt:21`）：

> 3. 以后要通知栏/耳机键/锁屏，`MediaSession` 直接接这个实例。

注释写着「以后」。所以现在：
- 手机本地播放时，**没有通知栏控制**
- **耳机线控/蓝牙耳机按键不生效**
- 锁屏看不到在放什么

**这条对自用影响很大** —— 你在手机上放歌，想暂停得回 App 里点。

**成本**：低到中（Media3 `MediaSessionService` 是现成的，主要是接 `PlaybackService` + 前台服务类型要新增 `mediaPlayback`）。

#### B3 · 真机自动化测试没落地

`docs/76` 写了方案，`scripts/lpdiag.py` 写好了 C 路（设备真值 + 声音判定已实测），
但：
- 没接进 CI
- A/B 路（截图/UI/点击）**一次真机都没跑过**

后果：每次改完只能你手动点一遍。**这是「每天都要用」的项目最该有的东西，也是最缺的。**

### C 类 · 自用特有缺口（产品不需要，自用很需要）

#### C1 · 配置备份/导出 —— **换手机就全丢**

**证据**：全仓 grep 无 `backup` / `export` 相关实现。

现在存在本地的配置：
- 设备列表（IP / uuid / 名字）
- 收藏 / 最近播放 / 歌单
- 电台收藏
- 洛雪脚本（`core-script` 存的）
- 播放输出选择

**换手机/重装 = 全部重配。** 自用项目尤其不能接受这个 —— 产品有云端同步，自用只能靠自己导出。

**成本**：低（一个 zip 导出 + 导入，纯文件操作，不需要新模块）。

#### C2 · 桌面快捷方式 / Widget —— 一键「客厅放歌」

自用的典型动作是固定的：「回家 → 客厅音箱 → 放我的常听列表」。
现在要：开 App → 设备页 → 点音箱 → 播放 → 进队列选列表。

一个桌面快捷方式（`ShortcutManager`）或者 Widget（Glance）能压成一下。
**成本**：低（快捷方式 50 行；Widget 要引 Glance，算新依赖）。

## 五、明确**不要**做的（避免过度建设）

| 不做 | 理由 |
|---|---|
| **不做通用蓝牙遥控** | 每个设备 40KB 逆向（`docs/82` 实测马桶案例）。自用最多 2-3 台设备，值不回成本 |
| **不做完整红外码库** | 只做「电视 + 空调 + 机顶盒」三类，按需下载（`docs/82` 已论证） |
| **不追求 publish 给别人** | `core-protocol` 的 `maven-publish` 配置可以留着，但**不为它牺牲任何设计** |
| **不做转码/媒体服务器** | tt-music 已经在那了，重复投资 |
| **不做音乐库管理** | NAS/Navidrome 的事。我们只做「浏览 + 投送」 |
| **不做多用户/分享** | 自用 |
| **不做 iOS** | 自用 |
| **不为了「架构纯粹」拆模块** | 8 个已经够多，再拆是负收益（见下） |

### 关于「还要不要新模块」

**我的判断：短期不需要新 Gradle 模块。**

理由：现在的 8 个模块边界是对的（每个都是「拖了装不下的依赖」才开的）。
剩下的缺口（A1/A2/A3/B2/C1/C2）**全是 app 层的编排和接线**，没有一个是「拖第三方依赖」。

**如果非要加，只有两个候选**：

| 候选 | 判据命中 | 建议 |
|---|---|---|
| `core-transfer`（本地↔设备搬播放） | 判据 2「有第二个消费者」？没有 | ❌ 放 app 层 |
| `core-ir`（红外码库） | 判据 4「带大体积资源」（4.8MB 码库） | ✅ 真要做红外才开 |

## 六、建议顺序

按「对定位的贡献 ÷ 成本」排：

| # | 做什么 | 为什么排这个位置 | 成本 |
|---|---|---|---|
| **1** | **MediaSession 接上**（通知栏/耳机键/锁屏） | 每天用；`LocalPlayer` 已经留好口；纯增量不改现有逻辑 | 低-中 |
| **2** | **统一入口（一个搜索框 + 分流）** | 定位的核心动作；只加不改，风险低 | 低 |
| **3** | **配置备份/导出** | 换手机就全丢，纯文件操作 | 低 |
| 4 | `core-discovery` 补测试 | 唯一的零测试模块 | 低 |
| 5 | 本地↔设备接续播放 | 体验好但不是每天用 | 中 |
| 6 | 真机自动化（`docs/76` A/B 路） | 长期收益最大，但需要手机常连 | 中 |
| 7 | 跨源队列（加 `source` 字段） | 只在你会攒混合歌单时才需要 | 中 |
| 8 | 红外（电视/空调/机顶盒三类） | 一年用几次 | 中 |
| 9 | 蓝牙 | 建议**不做** | — |

**前三项加起来大约「一周内的量」，但把定位从「一堆功能」变成「一个能天天用的东西」。**

## 七、给开发对话的执行清单（按顺序，可直接照单开工）

只列「现在就该做」的四项，都不动 `core-protocol`，都是 app 层接线。

### 第 1 项 · MediaSession（每天用，收益最大）

- 新增 `PlaybackService : MediaSessionService`，`MediaSession` 绑 `LocalPlayer.player`
- `AndroidManifest` 新增 `android:foregroundServiceType="mediaPlayback"` +
  权限 `FOREGROUND_SERVICE_MEDIA_PLAYBACK`
  **注意**：现有 `QueuePlaybackService` 是 `dataSync` 类型，**不能复用**（类型和权限一一对应）
- 验收：本地播放时通知栏出现媒体控件、耳机键能暂停、锁屏能看到曲名
- 参考 `docs/77` 第 2.1 节

### 第 2 项 · 统一入口（定位的核心动作）

- 一个输入框 + 并发问四个源（洛雪 / 电台 / NAS / 本地），各自返回「找到几条」
- **不做结果合并排序** —— 跨源排序没有意义（NAS 的《晴天》和网易云的《晴天》不是一回事）
- 纯编排，约 200 行 + 四个源各 30 行适配，**不开新模块**
- 验收：输入「周杰伦」，四个源各显示条数，点哪个源进哪个源的结果页

### 第 3 项 · 配置备份/导出

- 一个 zip：`SavedDevice` 列表 + 收藏 + 最近 + 歌单 + 电台 + `core-script` 的脚本 + `playback-output.txt`
- 纯文件操作，`runCatching` 包住，失败只记诊断
- 验收：导出 → `pm clear` → 导入 → 设备/收藏/歌单全部回来

### 第 4 项 · `core-discovery` 补测试

- 252 行、1 个文件、**连 `src/test` 目录都没有** —— 8 个模块里唯一零测试的
- 先把 SSDP 报文的解析拆成纯函数（可测），再补用例
- 验收：`core-discovery` 至少有 10 个离线用例，CI 加 `:core-discovery:test`
