## 一、为什么"读诊断"不够

诊断台能告诉你 **app 认为发生了什么**。但它永远回答不了这三个问题：

| 问题 | 诊断台能答吗 |
|---|---|
| 设备**真的**变了吗？ | ❌ 只能告诉你"我发了命令，收到 OK" |
| 声音**真的**响了吗？ | ❌ `curpos` 递增只证明"在解码" |
| 界面上**真的**显示对了吗？ | ❌ 报告里的字段和屏幕上的像素是两条路 |

**所以"开发不靠猜"的前提不是"能读日志"，而是"能拿到与 app 自述无关的第二、第三份证据"。**

---

## 二、三路对账（这是整个方案的地基）

| 路 | 拿什么 | 怎么拿 | 证明什么 |
|---|---|---|---|
| **A 界面** | 截图 + UI 树 | `adb exec-out screencap` / `uiautomator dump` | 用户看到什么 |
| **B 自述** | 诊断日志 + 报告 | `adb logcat -s LinkPlayDiag` | app 认为自己干了什么 |
| **C 真值** | 设备实际状态 | **直连音箱 `httpapi.asp`** | 设备真实是什么状态 |

**C 路是我们独有的优势**：三台音箱在局域网，`.226` 直连 curl 就行，不需要手机、不需要 root、不需要任何测试框架。

### 今天已经跑通的证据（不是设想）

```
$ python3 scripts/lpdiag.py device --all
✓ 192.168.99.153  doss3  fw=3.6.5310 vol=45 ch=0 stop  635/0ms      battery=50%  slaves=0  《Unknown》
✓ 192.168.99.164  doss1  fw=3.6.6623 vol=45 ch=0 pause 80062/700000ms battery=70% slaves=0  《001【战国】立木取信：商鞅变法》
✓ 192.168.99.181  doss2  fw=3.6.6623 vol=45 ch=0 stop  28978/322000ms battery=100% slaves=0  《Unknown》
```

一条命令同时拿到：固件版本 / 音量 / 声道 / 播放态 / 播放进度 / 曲名（hex 已解码）/ 电量 / 组网从机数。

**对账怎么用**：让 app 把音量调到 30，然后

- A 路：屏幕上是不是显示 30
- B 路：logcat 里命令发出去了吗、回包 OK 吗
- C 路：`vol` 真的是 30 吗

三份对不上 → 差异位置就是 bug 位置。**这才是"真解决问题"而不是"打个补丁试试"。**

## 三、要覆盖的全部功能面（诚实矩阵）

页面结构：**3 个一级 Tab**（设备 / 播放 / 媒体库）+ **10 个二级页**
（NAS / 本地队列 / 音乐库 / 电台 / 设置 / 配网 / 设备内容 / 在线 / WPS / 诊断）。

| 功能面 | 判定依据（C 路为主） | agent 能验吗 |
|---|---|---|
| 设备发现 / 在线状态 | 三台都在 + uuid 对得上 | ✅ |
| 连接 / 断开 | 真值 `reachable` 变化 | ✅ |
| 播放 / 暂停 / 停止 | 真值 `status` | ✅ |
| 音量（含手机音量键） | 真值 `vol` | ✅ |
| 声道 | 真值 `channel` | ✅ |
| 播放进度 / seek | 真值 `curpos` 递增或跳变 | ✅ |
| 队列（原厂 PlayQueue） | **UPnP `BrowseQueue` 直查** | ✅ |
| 多房间组网 / 拆分 | 真值 `slaves` + `slave_list` | ✅ |
| NAS 浏览 / 投流 | 真值 `status=play` + `totlen>0` | ✅ |
| 在线曲库（洛雪） | 搜索结果数 + `totlen>0` + `curpos` 递增 | ✅ |
| 网络电台 | 真值 `status=play` + `totlen=0`（直播流特征） | ✅ |
| 本地播放器 | **录音分析**（见第五节） | ⚠️ 要手机 |
| 诊断台自身 | 抓 logcat 里的 `[报告 N]` | ✅ |
| 崩溃 | `adb logcat -b crash` | ✅ |
| 界面渲染（红字错误 / 缺按钮） | 截图 + UI 树文字 | ✅ |
| **语音点歌** | 要人对着手机说话 | ❌ agent 不能替人说话 |
| **WPS 配对** | 要一台 WPS 设备 | ❌ 没设备 |
| **配网流程** | 会让音箱掉线重连 | ⚠️ 高风险，只做只读检查 |
| **界面好不好看** | 像素能看，审美不能 | ❌ 要人 |
| **跟不跟手 / 流畅度** | 能录屏，判断要人 | ❌ 要人 |
| **声音好不好听** | 只能判"有没有声"，不能判"好不好" | ❌ 要人 |

**这张表就是"全方位"的边界**。写清楚哪些验不了，比声称全能更值钱 —— 否则人会以为测过了。

## 四、要你做的：`testTag` 契约

**这是整个方案能不能自动化的唯一前提。**

现状：`uiautomator dump` 读 Compose 界面时，**可能把整页合成一个节点**，读不到任何按钮文字。真机没验过，但风险很高（Compose 的 semantics 默认不导出全部节点）。

要求（写进 `docs/52` 当硬规则）：

```kotlin
// 每个可点元素必须有稳定 testTag，命名 = 页面.功能
Modifier.testTag("player.playPause")
Modifier.testTag("home.deviceCard.${uuid}")
Modifier.testTag("sources.radio.add")
```

- **命名规则**：`<页面>.<功能>`，全小写驼峰，设备相关的带 uuid
- **不许用中文当 tag**（adb 传输编码不稳），中文留在 `contentDescription`
- **列表项必须带标识**，否则"点第 3 台设备的播放"没法表达

**为什么必须做**：没有 testTag，agent 只能按坐标点。分辨率、密度、字体缩放一变全废，而且测出来的东西没法复现。

**顺带要做的（`docs/75` 已提，仍然要）**：

- `am start --es diag 1` 的无 UI 触发口（不点界面也能出报告）
- `flush()` / `previous()` 两个死代码接上或删掉

## 五、工具形态：`scripts/lpdiag.py`

已经写好并在真机上验过 C 路。子命令：

```
# C 路（不需要手机，今天就能用）
device --all | --ip X --json        设备真值

# adb 通道
pair <ip:端口> <6位码>              首次配对（手机「无线调试」页）
connect <ip:端口>                   之后每次
devices                            列设备
shot [路径]                         [A路] 截图
ui [--json]                         [A路] UI 树（紧凑文本，只留文字+中心点）
tap "文字" | --xy X Y                [A路] 按文字点击
input "文字"                        [A路] 输入
app start|stop|clear                启动/停止/清数据
log [-f]                            [B路] 诊断日志
report [--save]                     [B路] 从 logcat 按 [报告 N] 拼回完整报告

# 声音（真响没响）
audio record --seconds 8            录环境音（拉起系统录音机）
audio analyze --file X.m4a          ffmpeg 测平均音量

# 编排
evidence [--name X]                 一键抓全套现场 → 证据包
run flow.json                       跑流程
```

**声音判定已实测**（用合成音频，不需要手机）：

```
tone.m4a     平均 -31.6 dB → 有声音   (exit 0)
silence.m4a  平均 -91.0 dB → 静音     (exit 2)
```

判据：`< -60dB` = 没出声，`-60 ~ -40` = 很轻，`> -40` = 有声音。

**这是"音箱真的响了没有"唯一客观的判据** —— `curpos` 递增只能证明在解码，证明不了喇叭在响。

## 六、流程格式（JSON，不引依赖）

```json
{
  "name": "音量与播放对账",
  "steps": [
    {"do": "clear"},
    {"do": "start"},
    {"do": "wait", "until": "ui:设备", "timeout": 10},
    {"do": "tap", "text": "播放"},
    {"do": "wait", "until": "device:192.168.99.164:status=play", "timeout": 8},
    {"do": "shot", "as": "01-playing"},
    {"do": "assert", "that": "device:192.168.99.164:totlen>0"},
    {"do": "audio", "seconds": 8, "expect": "sound"}
  ]
}
```

条件语法三种：

- `device:<ip>:<字段>=<值>` —— 对 C 路断言（**首选**）
- `ui:<文字>` —— 界面出现某文字
- `log:<正则>` —— logcat 命中

## 七、证据包（一次测试 = 一个目录）

```
runs/2026-11-04T12-30-01-音量与播放对账/
  00-摘要.json         设备真值 + 报告字数 + 崩溃行数
  device-truth.json    三台设备完整快照
  report.txt           完整诊断报告
  logcat.txt           全程诊断日志
  crash.txt            崩溃（有才生成）
  steps.json           每步：动作/耗时/是否通过/失败原因
  screenshots/         每步截图 + 失败现场 fail-NN.png
  audio/               录音片段
```

**为什么这么设计**：出问题时"最少要留下的东西"。缺一样后面就得猜 —— 而猜是我们最想消灭的东西。

## 八、硬规则（写代码时守住）

1. **断言只对 C 路（设备真值）**。对 A/B 断言等于让 app 自己给自己判卷。
2. **不许 `sleep`**，一律 `wait` 轮询到条件成立。`sleep` 是测试不稳定的头号来源。
3. **坐标不许写死**，一律按 `testTag` / 文字找。写死坐标的测试换个手机就废。
4. **任何断言失败立刻留现场**：截图 + logcat 尾部 + 设备真值快照。
5. **一条用例一个干净起点**：要能表达「冷启动」「热启动」「带数据启动」。
6. **测完恢复现场**：音量、播放、组网状态改过就要改回去（除非用例目的就是改）。

## 九、坑与未知

| 项 | 说明 | 状态 |
|---|---|---|
| **Compose 语义树** | 可能整页合成一个节点，读不到按钮 | ⚠️ **未验证，最大风险**。这正是要 testTag 的原因 |
| `uiautomator dump` 体积 | 原始 XML 比紧凑文本大 10–50 倍 | 已做转换（只留文字+中心点） |
| logcat 环形缓冲 | 默认 256KB 会被冲掉 | 已做 `logcat -G 8M` |
| `[报告 N]` 顺序 | 到达顺序 ≠ N 顺序 | 已做按 N 排序拼接 |
| `run-as` | 只对 debuggable 包有效 | 文档行为，未实测 |
| 无线调试端口 | Android 11+ 每次重启随机变 | 未实测；配对信息通常保留 |
| 录音机路径 | 不同 ROM 保存位置不同 | 未实测，可能要适配 |
| 息屏 | `input` 会先亮屏，可能点到锁屏 | 要设「充电时不锁屏」 |
| 安全性 | 无线调试开着时同网段任何人都能配对 | 用完就关 |
| 配网用例 | 会让音箱掉线重连 | 只做只读，写操作要人确认 |
