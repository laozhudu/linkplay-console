## 零、两个问题的直接答案

| 问题 | 答案 |
|---|---|
| **Xbox 360 有红外码吗** | **有。** `Consoles/Microsoft/XBOX360_Media.ir`，27 个键，**全部 raw**，含 `On` / `Off` |
| **能用吗** | 技术上完全能发（38kHz / 135 个时序点，在 `ConsumerIrManager` 能力内）。但「能不能真的开关机」**必须上机试**，三条我无法在这里验证 |
| **按需下载可行吗** | **可行，而且比全量内置更好。** 索引只要 **199KB（gzip）**，单设备文件中位 **3.6KB** |
| 真正的坑 | 不是下载，是**按键名归一化**：全库 54,415 种键名，电源类写法 2,900 种 |

## 一、Xbox 360：码确实有，而且带开关机

### 实测内容（码库里真实存在的 4 个微软文件）

| 文件 | 键数 | 类型 | 含电源键 | 键名样本 |
|---|---:|---|---|---|
| **`XBOX360_Media.ir`** | **27** | **全 raw** | ✅ `On` / `Off` | On, Off, Guide, Play, Pause, Stop, Rewind, Fast_Forward, Prev_chapter, Next_chapter, Dvd_menu, Title, Display, Info, Back, OK, Up, Down, Left, Right, A, B, X, Y |
| `XBox_DVD_Media_Playback_Kit.ir` | 27 | 全 raw | ❌ | Display, Reverse, Play, Forward, Skip -, Stop, Pause, Skip +, Title, Up, Info, Left, Select, Right, Menu, Down, Back, 1–9… |
| `Xbox_One_Media_Remote.ir` | 37 | — | ✅ `Power` | Power, Home, Up, Down, Left, Right, A, B, X, Y, Menu, Play_Pause… |
| `Xbox.ir` | 7 | — | ✅ `Xbox_POWER` | Xbox_POWER, Xbox_up/down/left/right, Xbox_select, Xbox_back |

**`XBOX360_Media.ir` 的 `On` 码实测长这样：**

```
name: On
type: raw
frequency: 38000
duty_cycle: 0.330000
data: 2650 904 461 429 459 431 457 876 457 878 1317 901 ...   （135 个时序点）
```

38kHz 载波、135 个点、单条 16835 字节的文件。**格式和 `ConsumerIrManager.transmit(freq, int[])` 完全对得上，零转换。**

### 能不能真的用 —— 三条必须上机验证的

我在这里能确认的只有「码存在且格式可用」。以下三条**没有真机验证，不能当结论**：

| 待验 | 为什么重要 |
|---|---|
| Xbox 360 主机前面板有没有 IR 接收器、朝哪个方向 | 有接收器才谈得上遥控。据公开资料 360 前面板有，但没实测 |
| 关机后是否仍供电给接收器（能否 IR 开机） | `On` 码存在说明**大概率可以**，但码库不保证它对 |
| `On` 和 `Off` 是两个独立码还是一个 toggle | 如果电视那样是 toggle，`On` 码在开机状态下会把机器关掉 |

**建议验证方式**：拿到码之后先只发 `Guide`（最安全，只是唤起引导界面），确认有反应再试 `On`。

### 一个现实提醒

Xbox 360 的主要交互（游戏）**走不了红外**——手柄是 2.4G 无线，红外只能干媒体遥控那点事（播放/暂停/方向/ABXY）。所以「用手机控 Xbox 360」的实际价值是「当个媒体遥控器」，不是「替代手柄」。

## 二、「按需下载」：数据说完全可行

用户的思路是「根据常用设备自动下载需要的红外码，不用背那么多」。这个思路是对的，而且比全量内置**明显更好**。实测数据：

### 体积对比

| 方案 | 体积 | 问题 |
|---|---:|---|
| 全量内置 | **62 MB** | APK 现在才 19MB，翻三倍，不可接受 |
| 内置家用核心 10 类 | 4.8 MB | 可接受，但仍背着一堆用不到的 |
| **内置索引 + 按需下载** | **199 KB（gzip）** | ✅ **推荐** |

### 索引到底多大（实测算的，不是估的）

| 索引形态 | 原始 | gzip |
|---|---:|---:|
| 纯路径（8,901 条） | 396 KB | **69 KB** |
| 路径 + 字节数 + sha256 前 16 位 | 623 KB | **199 KB** |

**199KB 塞进 APK 毫无压力** —— 相当于现在 `core-lx` 资源（628KB）的三分之一。

### 单设备下载量

| 指标 | 值 |
|---|---|
| 单文件中位大小 | **3.6 KB** |
| 最大单文件 | 1.0 MB（异常值） |
| 实测拉取 `XBOX360_Media.ir` | 16.8 KB / **0.62 秒** |

**一次下载一个设备，中位 3.6KB。** 就算用户配 20 个设备，总共也就几十 KB。

### 品牌维度：试错成本可接受

这是决定「按需」体验好坏的关键——一个品牌下有几个候选文件，用户要不要试几十次？

| 品类 | 品牌数 | 平均文件/品牌 | 最多的 |
|---|---:|---:|---|
| **TVs** | 117 | **3.4** | Samsung 57、LG 37、Sony 26 |
| **ACs** | 96 | **1.6** | LG 9、Daikin 9、Panasonic 5 |

**大多数品牌 1–3 个文件**，试错 1–3 次就能试到。只有 Samsung/LG 这种大厂例外（57 个），但那也正好说明「按需」的必要性——真全量内置，用户要在 57 个 Samsung 文件里翻，更糟。

### 所以正确的产品流程是

```
用户选「电视」→ 选品牌「Sony」→ 列出 26 个候选（只显示型号/文件名）
  → 点「试电源」→ 下载那 1 个文件（3.6KB）→ 发一条 → 用户看有没有反应
  → 没反应换下一个（已缓存的直接用，没缓存的再下 3.6KB）
```

**「自动下载」的边界**：能自动到「品类 + 品牌」这一级（从索引里查），**型号必须人来选**——因为红外无回执，只有人能判断「响没响」。

## 三、真正的坑：按键名归一化（这条比下载难十倍）

「自动下载」只解决「拿到码」。拿到之后要能显示成用户认得的按钮，这才是难点。

### 实测：全库键名极度混乱

| 口径 | 不同键名数 |
|---|---:|
| 全库（含 `_Converted_`） | **54,415 种** |
| 剔除 `_Converted_` 后（1,957 个文件 / 36,017 键） | **8,152 种** |

`_Converted_` 那 6,944 个文件是脚本批量转的，键名长这样：`116,15`、`5,-1` —— 纯坐标，没有语义。

### 电源键的 2,900 种写法

```
POWER 8422   Power 1053   POWER_ON 760   POWER_OFF 741   OFF 293   Off 207
STANDBY 137   TV_POWER 113   On 111   POWER_TOGGLE 67 …
```

同一个意思，至少十几种写法，大小写还不统一。

### 但归一化能覆盖大部分（这是好消息）

| 指标 | 实测 |
|---|---|
| 前 50 个键名覆盖 | **49.1%** 的条目 |
| 前 100 个键名覆盖 | 57.3% |
| **每个设备文件里能找到「电源键」的比例** | **84.1%**（1,646 / 1,957） |
| 能找到「音量键」的比例 | 48.2% |
| 有方向键组（≥3 个）的比例 | 39.7% |

**84.1% 的设备文件能找到电源键** —— 这是「可用」的硬指标。找不到的那 16% 主要是视频会议设备、CCTV，本来就没电源键。

### 结论：需要一张别名表，不是写 8,152 个

一张约 **200 条**的别名表（正则/前缀匹配）就能把 84% 的设备映射出「电源/音量±/静音/方向/OK/返回/菜单」这几个通用按钮。
**剩下的键名原样显示**——用户看到 `FACELUMI` 也能猜出是补光，比我们瞎猜成「未知」好。

## 四、推荐架构

```
core-ir（纯 JVM，零依赖）
  IrIndex.kt        内置索引（199KB gz）：path / size / sha256 / 品类 / 品牌 / 键数
  IrKeyAlias.kt     约 200 条别名规则 → 通用按钮（电源/音量/方向/…）
  FlipperIrParser   解析 .ir（parsed + raw 两种）
  IrProtocol        13 个协议编码器（NEC/NECext/RC5/RC5X/RC6/Samsung32/SIRC/15/20/Kaseikyo/RCA/Pioneer/NEC42）
  IrLibrary         按品类→品牌→文件查询；本地缓存读写

app/transport/IrTransport.kt    ConsumerIrManager 封装（~40 行，含 hasIrEmitter 检测）

码库托管：**镜像到我们自己的仓库/Release**，不直连 GitHub raw
```

### 为什么必须镜像，不能直连 raw

| 风险 | 说明 |
|---|---|
| 国内可达性 | `raw.githubusercontent.com` 时通时不通，手机侧比这台服务器更糟 |
| 上游消失 | 仓库改名/删除/归档，功能直接死。**CC0 允许我们再分发，这是应该用上的权利** |
| 版本漂移 | 上游更新后文件路径变了，索引里的 sha256 校验会失败，要能提示「码库已更新，请刷新」 |

**做法**：把 62MB 打成按品类分卷的 zip 放进我们自己的 GitHub Release（CC0 无限制），
索引里存「卷名 + 偏移」，单设备下载时按需拉对应卷（或者干脆每个品类一个 zip，TVs 1.2MB、ACs 1.4MB）。

### 三种下载粒度可选

| 粒度 | 首次下载 | 优点 | 缺点 |
|---|---|---|---|
| 单文件 | 3.6 KB | 最省流量 | 请求次数多，GitHub 侧可能限速 |
| **按品类** | TVs 1.2MB / ACs 1.4MB | **一次拉够，离线可用** | 首次稍大 |
| 按品牌 | ~50KB | 折中 | 需要预先切包 |

**建议按品类**——1.2MB 换「这个品类的设备全离线可用」，值。

## 五、坑清单

| 坑 | 说明 |
|---|---|
| **红外无回执** | 发出去不知道成没成。**只能靠人眼确认**，界面必须写清「没反应就换下一个码」 |
| **`transmit` 是同步的** | 长序列（Xbox 的 135 点）会阻塞，必须放后台线程，不能在主线程发 |
| **pattern 长度最好偶数** | pattern 是 on/off 交替的微秒序列（从 on 开始）。实现上通常要求以 off 结尾，奇数长度可能抛 `IllegalArgumentException`。**这条按 AOSP 行为推断，官方 API 页没明写**，编码器里补一个 0 兜底最省事 |
| **载波频率要对** | 多数 38kHz，但 RC5 是 36kHz、Sony 是 40kHz。要用 `getCarrierFrequencies()` 检查手机支不支持 |
| **`duty_cycle` 用不了** | `.ir` 里有这个字段，但 `ConsumerIrManager` 不提供占空比控制，忽略即可 |
| **`Unknown` 键 8,045 条** | 全库里这么多键没名字，只能原样显示 `Unknown` |
| **同一型号多份码** | Samsung 57 个 TV 文件，可能是不同年份/地区。**不能按型号字符串去重** |
| **空调码是状态机** | 空调一条码包含「模式+温度+风速」全状态，不像电视那样单键独立。**这是完全不同的交互模型**，别和电视混在一起做 |
| **手机没红外就整个不存在** | 必须先 `hasIrEmitter()`，没有就完全不渲染入口 |

## 六、分阶段建议

| 阶段 | 内容 | 前置 |
|---|---|---|
| **0** | 加 `hasIrEmitter()` 检测 + 隐藏入口，试发一条已知 NEC 码。**先确认你的手机有没有红外** | 无 |
| **1** | 解析器 + 13 个协议编码器（纯 JVM，可单测） | 阶段 0 有红外 |
| **2** | 索引 + 别名表 + 按品类下载 + 本地缓存 | 阶段 1 |
| **3** | 电视/机顶盒 UI（品类→品牌→试电源） | 阶段 2 |
| **4** | Xbox 360 这类游戏机（27 键，媒体遥控） | 阶段 3 |
| **5** | 空调（完全不同的状态机模型，单独设计） | 阶段 4 |

**阶段 0 几乎零成本，建议先做**——它决定了后面五步有没有意义。

## 七、一句话

**Xbox 360 的码确实有（27 键、全 raw、含开关机），「按需下载」也完全可行（索引 199KB、单设备 3.6KB）——真正的工程量在「把 5 万种键名归一成用户认得的按钮」和「把码库镜像到自己手里」，不在下载。**
