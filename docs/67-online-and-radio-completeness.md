## 一、结论先说

**两个模块的"不完善"性质完全不同，不能一起看。**

| 模块 | 代码完善度 | 内容可用性 | 真机验证 | 结论 |
|---|---|---|---|---|
| **电台** | 8.5 / 10 | **8 / 10** | **5 个内置台全部实测过** | **基本完善，能用** |
| **在线曲库** | 7 / 10 | **0 / 10** | 只验过 ping | **代码做完了，但没内容** |

**一句话**：电台是"能用但有边界缺口"；在线曲库是"**代码没问题，但曲库是空的**"。

## 二、电台：基本完善，有真实测记录

### 做得好的（超出预期）

**1. 5 个内置电台全部有真机验证记录**

`VerifiedRadioCatalog` 里每条都带 `deviceVerifiedAt` 字段：

| 电台 | 实测记录 |
|---|---|
| Radio Paradise | 2026-11-02 DS-1831 实测 play 且 curpos 递增 |
| NPR News | 2026-11-02 DS-1831 实测 play 且 curpos 递增 |
| FIP | 2026-11-02 DS-1831 实测 play |
| CNR 中国之声 | 2026-11-02 DS-1831 实测 play 且 curpos 递增 |
| CNR 音乐之声 | 2026-11-02 DS-1831 实测 play 且 curpos 递增 |

**这个设计很好**：验证结果写进代码，以后能复核，不是"我记得试过"。

**2. 5 个台全是 `http://`，没有 https**

作者已经遵守了"音箱不认 https"这个约束（`docs/42` 实测：https 命令回 OK 但没播）。

**3. 起播前必须先切输入源**

`RadioViewModel.playUrl` 里第一步就是 `switchmode:wifi`，然后才发 `playUrl`。
这是踩过的坑（旧固件只把地址存进 uri，不会真播），已经固化了。

**4. 用 6 秒轮询判定真实状态，不信命令回 OK**

```kotlin
repeat(6) {
    delay(1000)
    val st = PlayerStatus.parse(client.send(deviceIp, getPlayerStatus()))
    if (st?.playState == PlayState.PLAY) { playing = true; return@repeat }
}
```

这正是"命令回 OK ≠ 功能生效"的落实。

**5. 地址校验、归一化、按设备过滤、失效标记都做了**

- `validate()`：只接受 http/https，拒绝 `file://`
- `normalizeUrl()`：缺 `http://` 自动补
- `forDevice()`：按设备名过滤（不同音箱可以有不同电台列表）
- `markInvalid()`：播不了的台能标记

### 有缺口的三处

**缺口 1 · 允许输入 https，但设备播不了**

```kotlin
private val SUPPORTED_SCHEMES = listOf("http://", "https://")   // ← 允许 https
```

而 `RadioViewModel:207` 的注释已经知道这事：

> 命令全回了 OK，但状态没变成 PLAY —— https 在老固件上就是这个表现。

**问题**：允许输入一个必然失败的地址，用户要等 6 秒轮询才知道失败。

**建议**：输入 https 时**当场提示**「音箱不认 https，可能播不了，要试吗？」——
让用户有知情权，而不是等 6 秒后看到"失败了"。

**缺口 2 · 没有预检**

添加电台时只检查"像不像 URL"，不检查"能不能连上"。
用户加一个死链，要等播放时才发现。

**建议**：添加时做一次 HEAD 请求（2 秒超时），不通就提示"这个地址连不上，仍要添加吗？"

**缺口 3 · 失败后没有建议**

播失败只说"失败"，不告诉用户"换个台"或"这个台可能需要 https"。

## 三、在线曲库：代码做完了，但曲库是空的

### 实测证据（2026-11-04 现查）

```
服务在线：  {"status":"ok","type":"lxserver","openSubsonic":true}
专辑列表：  {"albumList2":{"album":[]}}
搜索测试：  {"searchResult3":{"song":[],"album":[],"artist":[]}}
扫描状态：  {"scanning":false,"count":0}     ← 曲库 0 首
```

### 但根因不是"没扫库"，是**目录根本不存在**

我上 SSH 查了 `.124`：

```
/vol2/1000/ttmusic/music/
  ├── cache/      （1042 字节）
  └── download/   （0 字节）
  ✗ local_lib/    ← 不存在
```

而 tt-music 容器的挂载是：

```
/vol2/1000/ttmusic/music  ->  /server/music
```

所以它期望在 `/server/music/local_lib` 找音乐，**那个目录不存在，扫也扫不出东西**。

### 音乐其实有，但在另一台机器上

| 位置 | 音频文件数 | 内容 |
|---|---|---|
| `.223` `/vol1/1000/储存空间1文件/音乐/` | **2433** | 真音乐（含无损，如"卢冠廷《Movie to Music》24-96"） |
| `.124` `/vol2/1000/备份/凯叔讲故事/` 等 | 913 | **评书 + 英语教材**，不是音乐 |
| `.124` `/vol2/1000/ttmusic/music/` | **0** | 空 |

**所以音乐在 `.223`，tt-music 跑在 `.124`，两者不通。**

### 三条解决路径

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 复制** | 把 `.223` 的音乐复制到 `.124` 的 `ttmusic/music/local_lib` | 占 `.124` 空间，且两份数据要同步 |
| **B. 挂载** | `.223` 的音乐目录通过 NFS/SMB 挂到 `.124`，再软链进 ttmusic | 要配 NFS，但只存一份 |
| **C. 不用 tt-music** | 直接用 `nas/` 模块走 `.223:8200` 的 DLNA（**已有 1931 首，已实现，能用**） | 零成本，但没有 Subsonic 的搜索能力 |

**C 其实已经可用了** —— `nas/` 模块就是干这个的，1931 首能浏览能播。
tt-music 的额外价值只有"按关键词搜"（Subsonic `search3`）。

所以问题变成：**为了"能搜索"，值不值得把 2400 个文件搬到 `.124` 或配 NFS？**

### 所以"不能用"不是 App 的问题

App 侧的代码是完整的：

| 能力 | 状态 |
|---|---|
| 认证（token + salt + md5） | ✅ |
| 错误处理（不是 Subsonic 响应 / status != ok 都有明确报错） | ✅ |
| 直链（`stream.view` 带凭据，**不需要 RelayMediaServer 转发**） | ✅ |
| 封面 | ✅ |
| 超时（connect 6s / read 12s） | ✅ |
| 诊断（`SubsonicSourceStatus`，刚由 #75 补上） | ✅ |

**卡点在 `.124`：没有扫库。**

`docs/55` 里早就记了这个待办：
> tt-music 曲库为空，需在 `.124` 界面里扫 `/vol2/1000/ttmusic/music/local_lib`

### 但代码层面也有两个真缺口

**缺口 1 · 没有分页**

```kotlin
"&songCount=${limit.coerceIn(1, 200)}"
```

最多 200 条，**没有分页**。搜一个常见词（比如"周杰伦"）如果有 500 首，
只返回 200，用户不知道还有更多。

**缺口 2 · 只有搜索，没有浏览**

对比标准 Subsonic 客户端（Navidrome / DSub / play:Sub），它们有：
- 浏览专辑 / 艺术家
- 播放列表
- 收藏 / 评分
- 最新添加 / 随机

我们只有"搜 + 播"。

**这是有意为之还是遗漏？**

`docs/06` 定过位：**"遥控器 + 检索层"（选 B）**，内容由 tt-music 提供，
我们不做完整音乐客户端。

所以"只有搜索"**符合定位**。但如果曲库有内容之后，用户可能会觉得"找不到想听的"——
因为不知道库里有什么，只能靠猜关键词。

**建议**：至少加一个"浏览专辑"（`getAlbumList2` 已经有接口，一次调用的事），
让用户能看到库里有什么。这不是"做完整客户端"，是"让检索有入口"。

## 六、建议

### 需要你先决策（不依赖开发对话）

**在线曲库要不要继续投入？**

| 选择 | 后果 |
|---|---|
| **A. 不投入**，用 `nas/` 模块（已有 1931 首） | 省事。代价：只能浏览，不能按关键词搜 |
| B. 把音乐复制到 `.124` | 能搜索。代价：占空间、两份数据 |
| C. 配 NFS 挂载 | 能搜索且只存一份。代价：要配 NFS，增加故障点 |

**我的建议：A**。理由：
1. 你已经能用 NAS 浏览 1931 首
2. `nas/` 模块已实现且验证过
3. "按关键词搜"这个能力，可以用 NAS 的 `ContentDirectory.Search` 补（DLNA 标准动作，比搬 2400 个文件便宜得多）

**如果选 A，在线曲库模块就该标成"预留/未启用"**，而不是"待完成"——
否则以后每次看进度都会以为它欠着什么。

### 给开发对话的三个小缺口（不急，可插在批次 1 之后）

| # | 缺口 | 成本 |
|---|---|---|
| 1 | 电台输入 https 时当场预警 | 低 |
| 2 | 添加电台时做一次 HEAD 预检 | 低 |
| 3 | 在线曲库加"浏览专辑"（`getAlbumList2` 已有接口） | 低 |

**都不影响批次 1 的进度**，可以等它做完六个源再提。

## 七、一句话总结

**电台：完善了，能用，5 个台真机验证过。** 剩下三个小缺口是"体验"不是"功能"。

**在线曲库：代码完善了，但 `.124` 上根本没有音乐** —— 音乐在 `.223`（2433 个文件），
tt-music 在 `.124`，两者的目录不通。

**而且你现在已经有一个能用的内容源**：`nas/` 模块走 `.223:8200` 的 DLNA，1931 首能浏览能播。

所以"在线曲库不可用"**不是缺陷，是重复投资** —— 除非你特别需要"按关键词搜索"这个能力，
否则把音乐搬到 `.124` 或配 NFS 的收益，比不上直接用已有的 NAS 源。
