# WG / Tailscale 穿透可行性调研（仅调研，不改任何网络配置）

> 场景：人在外地，想控制家里这台 DOSS DS-1831（`192.168.99.0/24`），并让它出声。
> 结论先行，依据随后，最后给一份「如果要做，怎么验证」的清单。

## 0. 结论

| 层面 | 能否过 VPN | 说明 |
|---|---|---|
| **控制面**（httpapi `/httpapi.asp`、UPnP SOAP `/upnp/control/*`） | ✅ **能** | 纯单播 TCP（80 / 49152）。只要设备 IP 可路由，WG 与 Tailscale 子网路由都能通 |
| **发现面**（SSDP 组播 `239.255.255.250:1900`） | ⚠️ **默认不能，但有替代** | 组播不过 VPN；不过这台设备**实测支持单播 M-SEARCH**，直接把包发给它的 IP 就能拿回 `LOCATION` |
| **媒体面**（手机当文件服务器，音箱拉流） | ❌ **不能** | 音箱要主动 `GET http://<手机IP>:<端口>/t/<id>`。音箱上没有 VPN 客户端、也没法配静态路由 → 它永远到不了你手机的 VPN 地址 |
| 媒体面（内容放在**家里**的 NAS/PVE 上，音箱拉） | ✅ **能** | URL 指向局域网地址（如 `http://192.168.99.124/...`），音箱在自己网段内直接拉，与你在哪无关 |

一行话：**远程「遥控」可以，远程「把我手机里的歌推给家里音箱」不行**——除非歌在家里那台常开的机器上。

## 1. 为什么媒体面是死路（这条最容易被忽略）

整列表推送 / 单曲投流的本质是：

```
手机 App  ──SOAP──►  音箱:49152   "去拉 http://<手机IP>:8123/t/42"
音箱      ──HTTP──►  手机:8123    ← 这一跳是音箱发起的
```

第二跳是**音箱作为客户端**主动连手机。跨 VPN 时：

- 你在外地，手机在 Tailscale/WG 网段（如 `100.64.x.x` 或 `10.6.0.x`）；
- 音箱只认识 `192.168.99.0/24` 和它自己的默认网关；
- **音箱不会跑 tailscaled**，也**没有「静态路由」配置项**（`getStatusEx` 里没有任何路由相关能力，Web 配置页只有 Wi-Fi）；
- 所以音箱发往 `100.64.x.x` 的包会被它自己的默认网关丢弃。

这不是协议限制，是**拓扑限制**：DLNA 渲染器是"拉流方"，它拉不到隧道另一端。

### 唯一可靠的解法：把内容挪到家里

| 做法 | 说明 |
|---|---|
| 内容放 NAS/PVE（`192.168.99.124` 等） | 音箱拉本地地址，一次配好永久可用；你在外地只需发控制指令 |
| 家里常开一台机器跑我们的 `LocalMediaServer` | 同一思路，只是换成自建服务；家里本来就有一堆常开设备 |
| 手机侧**下载到家里**再推 | 绕一圈，体验差，不推荐 |

**实践建议**：整列表推送这个功能，真正的落点是「家庭媒体服务器 + 音箱」，手机 App 只做控制端。
这也解释了为什么 Music Assistant / Navidrome 这类"服务端驻留"的方案是这个生态的主流。

## 2. WireGuard

### 2.1 事实

- WireGuard **只转发单播**。它没有组播/广播的传输机制（这是设计上的简化）。
- 跨网段访问靠 `AllowedIPs` 把对端网段写进来（子网路由），例如把 `192.168.99.0/24` 放到客户端的 `AllowedIPs`，同时在服务端配 `iptables`/`nftables` 转发与 NAT。
- 组播要过 WG 必须另外做：`ip link set wg0 multicast on` + `smcroute`/`igmpproxy` 这类组播路由（社区有成功案例，但配置复杂）。

### 2.2 SSDP 的额外门槛（比组播路由更麻烦）

SSDP 的 M-SEARCH 包 **TTL = 1**，设计上就"不出本地链路"。即使做了组播路由，
TTL=1 的包到了路由器就被丢弃。社区常见做法是：

1. 调高发送端 TTL（`iptables -t mangle ... TTL --ttl-set`），或
2. 用 **SSDP 代理/中继**（在两端各跑一个进程转发 M-SEARCH 与响应），或
3. **干脆不依赖发现**：把设备 IP 写死。

### 2.3 对本项目的建议（WG 路线）

| 需求 | 结论 |
|---|---|
| 远程控制（音量/播放/状态/改名） | ✅ 客户端把 `AllowedIPs` 加上 `192.168.99.0/24` 即可 |
| 远程发现设备 | ⚠️ 不做组播。用**单播 M-SEARCH 发给已知 IP**，或让 App 记住上次的 IP+UUID（IP 会变，见 docs/08 §0） |
| 远程投流本地文件 | ❌ 不可行（§1） |
| 安全 | ⚠️ 设备的 `httpapi` **无鉴权**。把整个 `192.168.99.0/24` 放进 VPN 等于把家里所有设备暴露给任何一个 VPN 客户端。**建议只放 `/<32>` 单机路由**（只通音箱这一个 IP），而不是整段 |

> ⚠️ 本机现有 WG 拓扑（服务端在 `192.168.99.2`、`.5` 通 100 段、`.4` 通 200 段）属于生产配置，
> 本次**不做任何改动**。若将来要加，按「一次改一处 + 改前备份 + 改后验证」的既有规矩来。

## 3. Tailscale

### 3.1 事实

- Tailscale 是 WG 的托管版，同样是**点对点单播**。
- 有 **subnet router**（`--advertise-routes=192.168.99.0/24`）可以让远端设备访问该网段内的设备。
- **组播不支持**：官方仓库有长期 feature request（"Support for general purpose multicast"），社区结论明确：
  "Multicast UDP does not work across VPNs in general, and that includes tailscale"，
  mDNS/SSDP/AirPlay 这类依赖组播的发现都会失败。

### 3.2 对本项目的建议（Tailscale 路线）

| 需求 | 结论 |
|---|---|
| 远程控制 | ✅ 开 subnet router 即可，配置比 WG 简单（不用自己管密钥/NAT） |
| 远程发现 | ❌ 组播不行；同样退回「单播 M-SEARCH + 记住 IP/UUID」 |
| 远程投流本地文件 | ❌ 同 §1（音箱不会跑 tailscale） |
| 额外可能 | 若家里那台常开机器装了 Tailscale，你可以远程操作它，由它**在局域网内**给音箱投流 —— 这是唯一顺的做法 |

### 3.3 两者对比（就这个用例）

| 维度 | WireGuard | Tailscale |
|---|---|---|
| 远程控制设备 | ✅ | ✅ |
| 组播发现 | ❌（可折腾但 TTL=1 麻烦） | ❌（明确不支持） |
| 远程投流手机本地文件 | ❌ | ❌ |
| 配置成本 | 中（密钥、AllowedIPs、转发规则） | 低（subnet router 一条命令 + 后台批准） |
| 与家里现有设施契合 | 家里已有 WG 拓扑 | 需新增节点 |
| 建议 | 若只控一两台设备，**加单机 /32 路由**最省事 | 若以后要远程多台、还要手机直连，Tailscale 更省心 |

## 4. 结论性建议（三条）

1. **远程控制用 VPN，远程投流不要用 VPN**。控制面单播可通；媒体面必须把内容放在家里。
2. **发现不要依赖组播**。这台设备实测支持**单播 M-SEARCH**，App 侧只要记住「上次的 IP + UUID」，
   先用单播探一次，失败再让用户填 IP，比折腾组播路由现实得多。
3. **路由要最小化**。设备 `httpapi` 无鉴权，VPN 里只放它在用的那一个 `/32`，不要整段。

## 5.5 真机印证（本轮补）

原来第 1 节的判断「媒体面把内容放家里 NAS → ✅ 能」已被真机证实：

```
音箱直接播 http://192.168.99.223:8200/MediaItems/24.mp3 → PLAYING，进度正常
```

所以远程使用这套东西的正确形态是：

1. **内容在家里的 DLNA 服务器**（fnOS DLNA / MiniDLNA）——音箱自己拉，与你在哪无关；
2. **控制指令走 VPN**（控制面纯单播，能通）；
3. 手机不再需要当文件服务器（那条路本来也过不了 VPN）。

另外实测到：设备的 **UPnP 端口 49152 会间歇性消失**（httpapi 仍正常）。
跨 VPN 时这种掉线更常见，客户端必须做探活重连，见 docs/10 §5。
