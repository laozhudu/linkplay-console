# 78 · 动作耗时账本：跟不跟手、有没有绕路、是不是两处在管同一件事

> 写于 2026-11-04 · 依据 main `5f7babb`
> 用户：「考虑诊断台能否记录各种动作响应时间，可用于解决是否跟手，最短路径是否真正落地，
> 代码是否冗余，是否多套管理同一个功能的问题。即跟踪是否标准化和一致性。解决一些目前响应速度不快的问题。」

---

## 零、三行摘要

1. **以前的"耗时"散在日志里**：`log.timed` 记的是单次调用，想回答"刷新设备慢不慢"得自己在几十条日志里挑出来再加一遍 —— 而用户只会截图。
2. **现在是账本**：按动作名聚合，每个样本带「耗时 + 指令条数 + 成败」，并直接给出三个判据的结论。
3. **动作名改成枚举**：写错名字编译不过；CI 还会拦"声明了但没接上"和"id 不规范"。

---

## 一、它回答哪四个问题

| 用户的问题 | 账本里的答案 |
|---|---|
| **是否跟手** | 每个动作的耗时 + `<100ms 跟手 / <1s 偏慢 / ≥1s 慢` 三档评价 |
| **最短路径是否真正落地** | 每个动作**实际发了几条指令**，与"理论最少"对比；多了直接写"绕路" |
| **代码是否冗余** | 同一动作平均指令数明显高于理论值 = 有地方在旁路取数 |
| **是否多套管理同一功能** | 同一动作在 2 秒内被触发多次 = 两处代码各刷一次 / 事件绑了两遍 |

---

## 二、三个判据的具体阈值与来历

### 2.1 跟手：100ms / 1s

取自人机交互的经验值（100ms 内算即时反馈，1s 内算注意力不断），**不是硬标准**。
但比自己感觉靠谱 —— 项目已经因为"我觉得还行"错过两次真问题。

### 2.2 绕路：在线设备数 × 2

一次「刷新设备」的理论最少指令数 = **在线设备数 × 2**，因为最短路径是每台两条：

```
GetControlDeviceInfo   （音量/静音/声道/从机/整份 Status，含电量与设备名）
getPlayerStatus        （曲名/进度/播放态）
```

真机 80ms + 32ms。**多于这个数就说明有地方在旁路取数**（例如又发了一遍 `getStatusEx`）。
账本不猜，直接把"期望 6 条 / 实际平均 9 条 / 最多 12 条"写进报告。

### 2.3 重复触发：2 秒窗口

用户点一下只会有一次。出现两三次基本就是：
- 界面 A 和后台心跳 B 都在刷（心跳不记账，但它调用的**同一个用户动作**可能会）；
- 或点击事件绑了两遍。

**这是"同一能力多套入口"的现场证据。** 已知的现成例子：`refreshDevices()` 与 `refreshGroup()`
共用同一个动作名，因为它们本来就是同一件事的两条入口 —— 报警是对的，不是噪音。

---

## 三、实现上的三个决定

### 3.1 指令条数靠时间窗捞，不靠手动 `+= 1`

口令层已经收口到 `CommandTrace.DEFAULT`，每条记录都带 `atMs`。动作结束后按时间窗捞出来即可。
手动计数必漏 —— `docs/59` 的字节统计已经栽过一次（发送路径四种，每处写一次必然漏一处）。

**局限（写在代码注释里，也写在这里）**：两个动作真并发跑在同一窗口时，指令数会互相算进去。
用户操作基本串行，现在接受；真并发分析要看指令流水本身的时间戳。

### 3.2 为什么有 `begin/end`，不是只有 `measure`

本项目大量动作是"发起后异步完成"（探活、投流、起播轮询）。
`measure { launch { ... } }` 会在 launch 返回的瞬间结束，测出来的 **0ms 是假的** ——
这是最坏的一种错：报告说"跟手"，用户体感是卡。所以异步动作用 `begin()` + `end()`，两头分别放在协程内。

### 3.3 心跳不记账

心跳 3 秒一次会把平均值拉平，"跟不跟手"就没意义了。账本只收**用户主动触发**的动作，
心跳次数由各自的诊断段记。实现上是 `probeSaved(actionName: Action?)`：
心跳调用不传名，用户点刷新才传。

## 四、动作名为什么是枚举

字符串常量挡不住 `begin("setVolum")` 这种手误 —— 编译通过，报告里却多出一个永远只出现一次的动作。
枚举把这件事挪到**编译期**：名字只有那几个，写错就是编译不过。

配套的 `scripts/check-timing-names.py` 查类型系统管不到的两件事：

1. `id` 必须唯一、驼峰小写开头、不是类名；
2. **每个枚举值在 `app/src/main` 里至少有一处使用** —— 声明了没接上，等于对报告撒谎。

> 这个检查当场就抓到了两条：`LX_SEARCH` / `LX_IMPORT_SCRIPT` 声明了但还没接界面。
> 处理方式是**删掉**（等下批真正接上时再加回来），而不是写注释绕过检查。

## 五、报告长什么样

```
[响应耗时]
  最近 6 次（新→旧）
    20:31:12 refreshDevices 412ms 6 条指令（GetControlDeviceInfo/getPlayerStatus） 偏慢
        3 台
    20:31:09 setVolume 87ms 1 条指令（SetVolume） 跟手
    20:31:02 radioPlay 6.8s 8 条指令（SetVolume/PlayMedium/...） 慢  ← 失败
  按平均排（慢的在前）
    radioPlay 平均 6800ms / 最慢 8200ms / 2 次 · 4.0 条指令 · 失败 1
    refreshDevices 平均 412ms / 最慢 610ms / 5 次 · 6.0 条指令
  重复触发（2000ms 内同一动作多次）
    refreshDevices ×2 / 340ms  ← 可能有两处在刷同一件事
  绕路（实际指令数多于最短路径）
    refreshDevices 期望 6 条 / 实际平均 9.0 / 最多 12
```

严重度规则：最慢动作 ≥1s → WARN；发现绕路 → WARN。

## 六、已知局限（都写在代码注释里）

| 局限 | 影响 | 以后怎么办 |
|---|---|---|
| 并发窗口混算 | 两个动作同时跑时指令数偏高 | 改成按 trace 条目归属（要口令层带上动作 id） |
| 不含 Compose 重组时间 | 测的是"我们办完"，不是"像素更新" | 与 `docs/76` 的截图对账合并看 |
| 起播类动作天然慢 | `radioPlay` 要等 6 秒设备状态，平均必然上千毫秒 | 报告里区分"固定等待"与"真实往返"（待做） |
| 心跳不计入 | 后台链路变慢不会反映在账本 | 心跳有自己的段（组拓扑/设备段） |
