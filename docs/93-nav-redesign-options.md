### 三个必须先承认的问题

1. **维度混着用**：设备(对象) / 播放(动作) / 洛雪(品牌) / 媒体库(集合) —— 四格三种维度
2. **两个纯中转页**：`SourcesScreen`(46) 和 `MyMusicScreen`(232) 点进去只是再选一次
3. **最常用的埋最深**：诊断台要「媒体库 → 其它入口 → 诊断」三层

## 二、三个方案

### 方案 A · 按「对象」分

```
┌─────────┬─────────┬─────────┬─────────┐
│  出声   │  找歌   │  设备   │   我    │
└─────────┴─────────┴─────────┴─────────┘
```

| 格子 | 第一屏就是 | 里面还有什么 |
|---|---|---|
| **出声** | 当前在放 + 进度/音量 + **从哪出声**（每台设备一个口） | 队列、投流日志 |
| **找歌** | **搜索框 + 最近播放**（直接有内容，不是空壳） | 源筛选条：NAS / 本地 / 在线 / 洛雪 / 电台 / 歌单 |
| **设备** | 分组后的设备列表（我的音箱 / 其它播放设备） | **红外 / 蓝牙 / WiFi 遥控**（U3 做到就加） |
| **我** | 设置项列表 | 配网、脚本、备份、**诊断台** |

**13 个子页的去向**

| 原页面 | 去哪 |
|---|---|
| `SourcesScreen` (46) | **删** |
| `MyMusicScreen` (232) | **删**（内容并为「找歌」首屏） |
| `LxSearchScreen` (147) | 并入「找歌」（洛雪降为源筛选之一） |
| `RadioScreen` (273) | 并入「找歌」 |
| `NasScreen` (502) / `OnlineScreen` (283) / `LibraryScreen` (599) | 归属「找歌」，各自作为该屏的一种"视图"而非独立页 |
| `QueueScreen` (345) | 并入「出声」 |
| `DeviceContentScreen` (183) | 并入「出声」队列 |
| `ProvisioningScreen` (342) + `WpsGuideScreen` (161) | 合并进「我」 |
| `ScriptsScreen` (119) | 进「我」 |
| `DiagnosticsScreen` (135) | 进「我」，**但首屏给一个入口**（不再三层） |

**好处**：维度统一（都是名词），加新能力知道往哪放。
**代价**：**「找歌」这一格要重新设计**——它现在要把 6 个源收进一屏，是三个方案里工作量最大的。
**风险**：NAS 那 502 行是目录浏览树，塞进"一种视图"里可能挤。

---

### 方案 B · 按「打开就想干什么」分

```
┌─────────┬─────────┬─────────┬─────────┐
│  首页   │  在放   │  找歌   │  设备   │
└─────────┴─────────┴─────────┴─────────┘
                                              「我」→ 顶栏齿轮
```

| 格子 | 第一屏就是 |
|---|---|
| **首页** | 聚合：在放什么 + 三台状态（电量/在线）+ 最近播放 + 「全部播放」 |
| **在放** | 播放页（同方案 A 的「出声」） |
| **找歌** | 同方案 A |
| **设备** | 同方案 A |

**好处**：最贴合"私人遥控器"——打开就看家里设备怎么样。
**代价**：**「首页」和「在放」内容重复度高**（都在显示当前播放）。要么首页只放设备状态，要么两格信息打架。
**代价**：5 个入口变 4+齿轮，齿轮容易被当成"不重要的东西"，而里面装着配网——**新设备第一次用就得去那儿**。

---

### 方案 C · 精简 3 格

```
┌─────────────┬─────────────┬─────────────┐
│    在放     │    找到     │    设备     │
└─────────────┴─────────────┴─────────────┘
                                   「我」→ 顶栏齿轮
```

**好处**：格子少，每格都大，误触少。
**代价**：这个 App 已经有 17 个页面，3 格装不下 —— 那些页面会挤成"二级页里的二级页"，
**等于把中转页问题从一层变成两层**。

**我不推荐 C**：它是为了"看起来简洁"牺牲可用性，而用户抱怨的正是"找不到东西"。

## 三、对比

| 维度 | A 按对象 | B 按场景 | C 精简 3 格 |
|---|---|---|---|
| 维度统一 | ✅ 都是名词 | ⚠️ 首页/在放有重叠 | ✅ |
| 打开即办事 | ✅ | ✅✅ 首页一眼看全 | ✅ |
| 中转页清零 | ✅ | ✅ | ❌ 变两层 |
| 加新能力往哪放 | 清楚 | 要判断"算场景还是算对象" | 不清楚 |
| 工作量 | **大**（「找歌」要重做） | 中 | 小 |
| 主要风险 | NAS 目录树塞不下 | 首页与在放信息打架 | 层级变深 |

---

## 四、我的建议：**A，但保留 B 的一个东西**

选 **A（按对象）**，理由：这个 App 会一直加能力（红外、蓝牙、B站、下载……），
**只有"按对象分"在加东西时不会变**。按场景分，加一个新场景就得重排一次。

但把 B 的**首页聚合**吸收进来：

```
「设备」格的第一屏 = 分组设备列表 + 顶部一条"在放什么"摘要
```

这样既有 A 的稳定结构，又有 B 的"打开就知道家里什么状态"。

## 六、需要你定的三件事

1. **选哪个方案**（我建议 A + B 的首页摘要）
2. **洛雪降级**：它现在占一个底部格子，方案 A 里会变成"找歌"里的一个源。
   你搜洛雪很多的话，这个变化要你确认。
3. **诊断台放哪**：我建议「我」的首屏第一项（现在要点三层）。它是排障唯一入口。

## 七、明确不做

| 不做 | 理由 |
|---|---|
| 引入 Navigation Compose | 现在 13 个二级路由用枚举够用，换框架是纯成本 |
| 做侧滑抽屉 | 抽屉里的东西等于"藏起来"，和"不许中转"冲突 |
| 保留 `SourcesScreen` 作为"媒体库首页" | 它就是那个杂物间的门牌 |
| 一次改完 | 6 步分开，每步可回退 |
