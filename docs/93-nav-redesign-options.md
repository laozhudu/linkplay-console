## 一、大厂参照（这些模式已被几亿人验证）

| 产品 | 底部结构 | 借什么 |
|---|---|---|
| **Spotify** | Home / Search / Your Library | **搜索独立成格**（内容源的核心动作就是"找"） |
| **YouTube Music** | Home / Explore / Library | 同上；"在放"用一条常驻条而不是一个 tab |
| **Sonos** | 首页(房间) / 浏览 / 搜索 / 系统 | **遥控/房间独立成格**；系统设置退到最后 |
| **Google Home** | 设备 / 自动化 / 我 | 设备（遥控）是主体，设置退到第 3 格 |
| **Apple 家庭** | 家 / 自动化 / 发现 | 同上 |

**三条被反复验证的结论**：

1. **"找内容"必须独立成格**（Spotify/YouTube Music 都是），不能塞进"库"里再点一层
2. **"控设备"是主体之一，不是设置**（Sonos/Google Home 都给它独立格）
3. **"在放"不做 tab**，用常驻播放条 + 点开进全屏（YouTube Music/Spotify 都这样）
   —— 但本项目常驻条已存在（`MiniPlayerBar`），且播放页信息密度高，
   所以「播放」仍占一格（偏离一点点，理由见 §3）

## 二、定稿结构

```
┌─────────┬─────────┬─────────┬─────────┐
│  播放   │  内容   │  遥控   │   我    │
│   ▶     │   🔍    │   ◉     │   ≡     │
└─────────┴─────────┴─────────┴─────────┘
```

| 格子 | 它回答的问题 | 第一屏就是 |
|---|---|---|
| **播放** | 「现在放什么、怎么放」 | 封面 + 曲名 + 进度 + 音量 + **从哪出声**（每台设备一个口）+ 队列 |
| **内容** | 「有什么可放」 | **搜索框** + 最近播放 + 源筛选（NAS / 本地 / 在线 / 洛雪 / 电台 / 歌单） |
| **遥控** | 「这些机器怎么控」 | 分组设备列表（我的音箱 / 其它播放设备）+ 音量/组网/声道 + **红外 / 蓝牙 / WiFi 遥控**（U3） |
| **我** | 「App 自己怎么配」 | **诊断台（第一项）** + 配网 + 脚本 + 备份 + 关于 |

**为什么「我」里诊断台排第一**：它是排障唯一入口，现在要点三层。
一个自用工具，最常用的往往不是"功能"而是"出问题时看哪里"。

## 三、一处刻意的偏离（要说明白）

**大厂都把"在放"做成常驻条，不做 tab。** 我们保留一个「播放」格，理由：

1. 播放页 964 行，信息密度高（封面/进度/音量/队列/投流日志/预设键），
   常驻条点开是**全屏页**，不是"一条"能承载的
2. 本项目播放条已经存在（`MiniPlayerBar`），它在非播放页提供"一眼看到在放什么"，
   两者不冲突：条是摘要，格是全操作面

## 九、设备模型（用户 2026-11-05 澄清，**优先于上面所有结构细节**）

用户原话：「设备是需要添加的，现在没有并不意味着永远没有，这是由我软件功能确定的。
就是红外设备，蓝牙设备」+「用户不需要知道全部设备信息，用户只需要能用，好用，简单状态就够」。

### 设备是用户添加的，不是探测出来的固定列表

现在只有三台 DOSS + 一台电视盒子，**不代表以后只有这些**。
红外电视、空调、蓝牙遥控……都是"添加进来的"。

### 三种类型，同一套「添加 → 控制」

| 类型 | 例子 | 怎么添加 | 默认显示的状态 |
|---|---|---|---|
| **播放设备** | DOSS 音箱、DLNA 渲染器 | SSDP 发现 / 填 IP | 在放什么 · 音量 · 在线 |
| **红外设备** | 电视、空调、Xbox | 选品牌/型号（接码库后） | 最近按过的键 |
| **蓝牙设备** | BLE 遥控、耳机 | 扫描配对 | 连没连上 |

### 「输出口」不是独立概念

它是**播放设备里能出声的那些**。所以播放页的"从哪出声"列表 = 播放设备列表，
不是另建一套实体。

### 状态只留三样

在不在 / 在放什么（或最近干了什么）/ 音量（或电量）。

**电量、固件、能组网、支持什么协议 —— 这些是排查时才需要的，不进默认界面。**

（上一版我在分组标题下面写了一行"能收整份列表、能组网"，已删掉。
那是给开发看的，放在界面上只是噪音。）

## 十、设计语言：**Apple HIG**（用户 2026-11-05 定）

用户原话：「苹果的 ui 设计就是最好的 ui」

### 先说清一个冲突

**现在这个 App 的视觉是 Google Material 3，不是苹果。** 具体证据：

```kotlin
// Theme.kt:44
val AppShapes = Shapes(
    extraSmall = RoundedCornerShape(8.dp),   // Material 的形状阶梯
    medium = RoundedCornerShape(18.dp),
    extraLarge = RoundedCornerShape(32.dp),
)
// Theme.kt:174 / :197  → darkColorScheme / lightColorScheme（Material 色彩系统）
```

材料设计和苹果的差别不在圆角多少，在**结构**：
Material 用"卡片堆叠"，苹果用"分组列表"。现在全 App 有 **19 处 `AppCard`**。

### 八条落地规则（照着做，不要自由发挥）

| # | 规则 | 苹果的做法 | 我们现在的样子 |
|---|---|---|---|
| 1 | **分组列表优先，卡片极少用** | 设置/健康/音乐全是 inset grouped list | `AppCard` 19 处堆叠 |
| 2 | **大标题**（Large Title 34sp，左对齐，滚动收起） | 每个一级页顶部 | `PageHeader` 是小号标题 |
| 3 | **灰阶层级，颜色只给"状态"和"主操作"** | label / secondaryLabel / tertiaryLabel 三层灰 | 每处都在用 `primary` 彩色 |
| 4 | **图标是线性的，不是字符** | SF Symbols | 底部用 `◍ ▮▮ ♪ ≡` 字符当图标 |
| 5 | **每屏一个主动作** | 右上角一个文字按钮 | 有的页面三四个平级按钮 |
| 6 | **行内不放解释文字** | 一行一个意思，解释放下一层 | 已删一处（设备分组），其余还有 |
| 7 | **行高 ≥ 44dp，整行可点** | 触控友好 | 部分行只有小按钮可点（洛雪/电台已修） |
| 8 | **动效短促**（≤300ms，spring 收尾干净） | 不炫技 | 播放页有一处手挑的 bouncy spring |

### 与已有工作的关系（不用推倒）

| 已有 | 是否保留 |
|---|---|
| `PlayerUiState` / `PlaybackDispatcher` / 唯一入口 | ✅ 全部保留，与视觉无关 |
| 触感反馈（`AppCard` 里那处） | ✅ 保留，但要跟着卡片改到列表行上 |
| `AppPage` / `AppSearchField` / `AppListRow` / `AppStateCard` | ✅ 骨架保留，**样式按苹果规则调** |
| `AppCard`（19 处） | ⚠️ **逐步换成分组列表行**，不是一次删 |
| 字符图标（Tab glyph） | ❌ 换成线性图标 |

### 落地顺序（在导航重排的 6 步之前先做，因为样式是地基）

| 步 | 内容 | 收益 |
|---|---|---|
| **S** | 建三个苹果风格的基础件：`InsetGroup`（分组列表）、`ListRow`（标准行）、`LargeTitle` | 后面所有页面都有统一模子 |
| S+1 | 设备页换成分组列表（当前最乱的一页） | 一眼看到全部设备状态 |
| S+2 | 「我」页用分组列表 | 设置类页面天生适合 |
| S+3 | 播放页按 Apple Music 的 Now Playing 收一遍 | 大封面 + 简洁控制 |
| S+4 | 底部图标换线性图标 | 去掉字符的土味 |

**先做 S**：它是地基，不做 S 就直接改页面，等于每个页面各写一套。

### 明确不做

| 不做 | 理由 |
|---|---|
| 引入第三方 UI 库（如 Compose Material 3 Expressive 增强包） | 苹果风格本身就是"少"，加库只会加东西 |
| 一次性换掉 19 处 `AppCard` | 会同时动 10 个页面，出问题无法定位 |
| 改成 iOS 交互习惯（左滑返回等） | Android 用户会别扭；只借视觉语言，不借平台习惯 |

## 十一、设计判据：**呈现使用**，不是呈现功能

> 用户原话（2026-11-05）：「**之前开发是挖掘功能，ui 设计是呈现使用**」

### 这两件事的区别

| | 挖掘功能（前期） | 呈现使用（现在） |
|---|---|---|
| 问题 | 「这个能力通不通」 | 「用户在这里要完成什么动作」 |
| 界面 | 把挖到的东西都摆出来 | 把完成那个动作的路铺平 |
| 好界面 | 功能都找得到 | **一件事一次到位** |
| 典型错 | 分组说明、能力位、协议名 | —— |

**我之前一直在做左边那列。** 具体表现：

- 设备分组标题下写「能收整份列表、能组网」← 那是功能说明
- 播放页状态栏显示 `输入源 DLNA 渲染器` ← 那是协议名，用户不关心
- 设置项按"我们实现了什么"排列，不按"用户要改什么"排列

这些不是错，是**上一个阶段的产物**。挖掘阶段需要它们（否则不知道通没通），
呈现阶段它们就是噪音。

### 落地判据（每个界面先答这一问）

> **用户打开这个界面，是为了完成哪一个动作？**

答不出来，说明这个界面是"功能罗列"，不是"使用路径"。

| 界面 | 用户要完成的动作 | 所以第一屏必须有 | 所以不该有 |
|---|---|---|---|
| **播放** | 让声音从我想的地方出来 / 停一下 / 换一首 | 封面 + 播放键 + 进度 + **一个能立刻换输出口的东西** | 协议名、日志、队列详情（折叠） |
| **内容** | 找到一首我现在想听的 | 搜索框（自动聚焦）+ 最近播放 | 源分类说明、库统计 |
| **遥控** | 调某一台的音量 / 让它组网 / 开关某台遥控设备 | 一台一行的**可直接调音量** | 能力位、固件版本（进详情） |
| **我** | 出问题时看哪里 / 改个设置 | **诊断台第一项** | 功能清单 |

### 用它回答上一轮那个问题（行内数字 vs 行内滑块）

按"呈现使用"推：**这个 App 的本质是遥控器，调音量是最高频的动作。**

那就不能要求"点进设备 → 再调"——那是两步。

**选行内可拖（乙）**，但加两条约束：

1. 拖动区域在行**右侧一块**，不是整行（整行拖动会让"点进设备"变得难点）
2. 拖动时数字放大显示，松手发命令（不发连续命令 —— 音箱会卡）

苹果不给行内滑块，是因为 iOS 的"设备列表"不是遥控器；**我们这个是。**

### 一条推论：状态显示要"够用即停"

「需要知道」和「想知道」是两件事：

| 信息 | 用的时候需要吗 |
|---|---|
| 在不在线 | ✅ 需要（否则点了没反应） |
| 在放什么 | ✅ 需要（决定要不要切） |
| 音量 | ✅ 需要（这就是要调的东西） |
| 电量 | ⚠️ 排查时需要 → 进详情 |
| 固件版本 | ⚠️ 排查时需要 → 进详情 |
| 能不能组网 | ❌ 不需要知道，试一下就知道了 |
| 支持什么协议 | ❌ 用户不该看到这个词 |

**前三条进列表，后四条进详情。** 这就是"简单状态就够"的具体尺寸。
