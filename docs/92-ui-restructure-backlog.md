## 一、U1 · 底部导航重排

### 现状（提交 `49ce277` 之后）

```kotlin
enum class Tab { Devices("设备"), Player("播放"), Lx("洛雪"), Sources("媒体库") }
```

四个 tab，**13 个二级页面**：

```
Nas  LocalQueue  Library  Radio  Settings  Provisioning
DeviceContent  Online  Wps  Diagnostics  Scripts  LxSearch  SearchHub
```

### 为什么"不对了"

| 问题 | 具体 |
|---|---|
| **洛雪单独占一格** | 它是"一个内容源"，却和"媒体库/设备/播放"并列 —— 分类维度不一致 |
| **"媒体库"是杂物间** | 里面装 NAS / 本地 / 在线 / 电台 / 歌单 / 脚本 / 搜索中心，7 件事挤一个格子 |
| **电台没有 Home** | 一等能力，只能从媒体库里点进去 |
| **诊断台藏最深** | 它是最常用的排障入口（每轮都靠它），却埋在二级页 |
| **遥控类零体现** | 红外 / 蓝牙 / WiFi 一个入口都没有（见 U3） |

### 用户定的结论

> 「可以在后面全部完成底层架构完成再考虑如何设计才合理」

**所以本条不做设计，只锁定"必须重做"这件事和它的判据。**

### 重做时至少要满足（写在这里免得将来又凭感觉拍）

1. **一级入口按"对象"分，不按"播放 vs 遥控"分** —— 设备、内容、遥控、我（设置）
2. 同类能力不拆两格（洛雪和电台都属"内容源"，要么都在一级、要么都在内容里）
3. 每格点进去第一屏就得能办事，不许再出现"进去再选一次"的中转页
4. 底部最多 5 格（再多就换 `NavigationBar` 的 3 段式，不加大堆图标）

## 二、U2 · 首页设备必须按类型隔离

### 现状

`HomeScreen` 里所有设备**混在一个列表**：

```
doss1 (192.168.99.164)   ← LinkPlay 私有协议，能读电量/固件/组网/播放队列
doss2 (192.168.99.181)   ← 同上
doss3 (192.168.99.153)   ← 同上（旧固件 3.6.5310）
E900V22C-175[DLNA]       ← 通用 UPnP 渲染器，只能 Play/Pause/SetVolume/Seek
```

**两者能力差一个量级**：后者**没有** `PlayQueue`（没设备侧队列）、没有 `slave_list`（不能组网）、
没有电量/固件、没有 `httpapi` 私有命令。

全仓 `DeviceProfile.` 在界面上只有 1 处（`HomeScreen:303`，还是 `?: UNKNOWN` 兜底），
**也就是说界面上几乎完全没有区分这两类设备** —— 用户看到的是"四台一样的设备"。

### 用户要什么

> 「通用 upnp 设备根本就没考虑过与 doss 隔离，反而混在一起」

### 怎么做（等 S2.3 能力位补齐之后）

1. `DeviceCapabilities` 补两个根位：`canPlayAudio`（能播声音）/ `canBeRemoted`（能被遥控）
2. 首页按**能力**分组，不按品牌：
   - **我的音箱**（`supportsPlayQueue` + `supportsMultiroom`）—— 三台 DOSS
   - **其它播放设备**（`canPlayAudio` 但无队列/无组网）—— 电视盒子
   - **发现但未添加**（SSDP 扫到、还没保存）
3. 每组显示**它能干什么**，不显示它做不到什么（避免满屏"不支持"）
4. 界面里 `DeviceProfile.xxx` 判断归零（`scripts/check-profile-in-ui.py` 转 error）

## 三、U3 · 遥控类能力 UI 完全没有

### 现状

| 能力 | 代码 | 界面 | 状态 |
|---|---|---|---|
| **红外** | `ir/NecEncoder.kt` + `ir/IrBlaster.kt` + `ir/IrStatus.kt` | 只在**设备设置页**一张卡（试发一个键） | 只验过"有没有发射器"，码库没做 |
| **蓝牙** | 无 | 无 | 只调研完（`docs/84`） |
| **WiFi 遥控**（`docs/85`） | 无 | 无 | 只有方案 |

用户原话：「红外，蓝牙，wifi 等遥控，你也根本没有在 ui 上体现」。

### 为什么现在不该画入口

- **红外**：手机能不能发红外取决于有没有发射器（`hasIrEmitter()`），现在连这个都没确认过。
  而且 `ConsumerIrManager` **只有发送没有接收**，码库是唯一路径（`docs/81` 纠正了 `docs/49` 的错误前提）。
  画一个"遥控器"入口，点进去发现没有码库 = 假入口。
- **蓝牙**：`docs/84` 是调研，一行实现都没有。
- **WiFi**：`docs/85` 是方案。

**功能不存在的入口不画**（`docs/86` 的原则：界面只画能做的）。

### 什么时候画

| 前置 | 判据 |
|---|---|
| 红外 | ① 确认手机有发射器；② 接入码库（`Flipper-IRDB` CC0，30 万条）；③ 能发出一个真能控电视的键 |
| 蓝牙 | 至少能扫到并连上一台 BLE 遥控/耳机 |
| WiFi 遥控 | 确认目标设备（电视/空调）的协议，且有一条真机可用的命令 |

三条**任一**达到，就把该能力的入口加进 U1 重排后的导航（预计归到"遥控"一格）。
