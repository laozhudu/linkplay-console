## 二、五个真实问题（都能在代码里指到行）

### 问题 1 · `sub` 是单层，无法嵌套

`ConsoleApp.kt:122` `if (currentSub != null) { ... return }`

只有**一层**。想"内容 → NAS → 某个目录 → 该目录的歌曲列表"，第二层没地方放。
现在的规避办法是"把 NAS 的目录树做在同一页里"（`NasScreen` 502 行），
这一页承担了浏览、播放、队列三件事。

### 问题 2 · 返回目标写死，已经出错

```kotlin
SubPage.Diagnostics -> DiagnosticsScreen(onBack = { sub = SubPage.Settings })
```

但诊断台可以从**三处**进：设备页、我页、设置页。

于是：**我 → 诊断台 → 返回 → 落到「设置」页**。用户在"我"页点进来的，回不去"我"。

### 问题 3 · 任何 Tab 上按返回都会跳到设备页

```kotlin
BackHandler(enabled = sub != null || tab != Tab.Devices) {
    when {
        sub != null -> sub = null
        else -> tab = Tab.Devices
    }
}
```

在播放页按返回 → 跳设备页。**这是反 Android 标准的**：

| 平台 | Tab 根上按返回 |
|---|---|
| Android 标准 | 退出 App（或什么都不做） |
| iOS | 无效果（Tab 就是根） |
| Spotify / YouTube / Gmail | 退出 App |

而且"跳设备页"会丢掉播放页的滚动位置和当前上下文。

### 问题 4 · 同一个页面 6 个入口，返回全靠"回 Tab"

`Library` 有 6 个入口。每个入口退出都回当前 Tab —— 从内容页点"歌单"进去，选中一个歌单再返回，**回到内容页**（对的）；但用户想"回上一级歌单列表"时，没有上一级。

这是单层栈的必然结果：**没有"上一级"这个概念**。

### 问题 5 · 播放页既是 Tab、又是跳转目标

设备页点一台设备 → 跳 `Tab.Player`。但播放页是 Tab，**没有"返回设备页"这条路**（Tab 之间按返回是问题 3 的行为）。

大厂怎么处理这件事（Spotify）：Now Playing 是**从底部条 push 上来的**，下箭头 = pop 回进入前的页面。

## 三、大厂的四种层，各自解决什么

| 层 | 语义 | 关闭方式 | 例子 |
|---|---|---|---|
| **Tab** | 并列大类，**无历史** | 切走即可 | Spotify Home / Search / Library |
| **Stack（push）** | 深入一个对象，**有历史** | 返回箭头 / 系统返回 | 专辑 → 曲目；设备 → 设备详情 |
| **Sheet** | 临时任务，**可拖拽分档** | 下拉 / 点外部 | 播放队列、分享、目标选择（Spotify 的 Connect） |
| **全屏向导** | 一次性流程，**不能中途看别的** | 完成 / 取消 | 配网、首次启动引导 |
| **Alert** | 确认或报错 | 两个按钮 | 删除确认 |

### 三条被普遍遵守的规则

**规则 1 · Tab 不堆历史**
切 Tab 再切回来，位置保持，但**不产生返回记录**。返回键在 Tab 根上 = 退出。
（现在的"任何 Tab 按返回跳设备页"违反这条。）

**规则 2 · 每一层只有一个关闭方向**
push → 左滑/返回箭头 pop；sheet → 下拉；全屏向导 → 完成/取消。
现在的问题是**同一个东西有两个关闭语义**（比如播放列表用 Dialog，只能点完成/外部）。

**规则 3 · 临时任务用 Sheet，不用全屏**
Spotify 的队列、Sonos 的分组、Apple Music 的歌词，全是可拖拽的 sheet ——
因为"看一眼就走"的任务不该占满整屏，也不该进历史。

## 四、逐页建议（对照现状）

### 一级 Tab（保持 5 个）

| Tab | 该有的行为 |
|---|---|
| 播放 | 有设备时是可用的 Now Playing；**没设备时不该是空白页**，应显示"去添加设备" |
| 内容 | 搜索 + 投给 + 接着听 + 最近加入（已实现） |
| 设备 | 目标列表 + 发现（已实现） |
| 遥控 | 按键面板（等码库） |
| 我 | 诊断台第一项（已实现） |

### 二级：13 个该砍成 8 个

| 现在 | 建议 | 理由 |
|---|---|---|
| `Nas` + `LocalQueue` + `Library` | **合成 1 个「浏览」栈**（有层级） | 三者都是"一堆歌"，差别只在来源 |
| `Radio` + `Online` | 内容页内联的筛选结果，**不单独成页** | 它们本来就只是内容源的两种 |
| `SearchHub` + `LxSearch` | 合成 1 个搜索（结果按源分组） | 两个搜索框是历史遗留 |
| `Settings` | 保留（设备详情） | 从设备行进入 |
| `DeviceContent` | **并入 Settings** | 预设键/固件本来就是设备详情的一部分 |
| `Diagnostics` | 保留，但**从"我"进，返回回"我"** | 修问题 2 |
| `Provisioning` + `Wps` | 保留（全屏向导，正确） | 一次性流程 |
| `Scripts` | 并入「我 → 音源」 | 低频配置 |

### 模态：统一规则

| 内容 | 现在 | 建议 |
|---|---|---|
| 播放队列 | 全屏 Dialog | **BottomSheet（三档：收起/半屏/全屏）** |
| 目标选择 | 内联 chips | 保持内联（更快，不用开一层） |
| 长按菜单 | Dialog | 保持（Android 标准是 PopupMenu / ModalBottomSheet） |
| 配网 | SubPage | 保持（全屏向导正确） |
| 删除确认 | Dialog | 保持 |

## 五、跳转规则（建议写成约定）

```
Tab 切换        → 不产生历史；每个 Tab 记住自己的滚动位置
点对象          → push（有返回箭头）
看一眼就走      → sheet（可下拉关）
一次性流程      → 全屏向导（完成/取消）
确认/报错       → alert

返回键：
  有 sheet 打开  → 关 sheet
  有 push        → pop 一层
  在 Tab 根      → 退出 App（不是跳到别的 Tab）
```

## 六、优先级建议

| 优先 | 项 | 理由 | 代价 |
|---|---|---|---|
| **P1** | 修问题 2（诊断台返回落到错页） | **已经是 bug**，用户能撞到 | 小 |
| **P1** | 修问题 3（任何 Tab 按返回跳设备页） | 反标准，每天都会撞 | 小 |
| **P2** | 播放列表改 BottomSheet | 现在全屏 Dialog 过重 | 中 |
| **P2** | `sub` 换成每 Tab 一个栈 | 解决嵌套与"回上一级" | **大**（牵动 13 个页面） |
| **P3** | 砍二级页（13 → 8） | 减少层级本身 | 大 |
| **P3** | 播放页"从设备进"的返回语义 | 要么给播放页一个 pop 路径，要么接受 Tab 语义 | 中 |

## 七、一处值得单独讨论的取舍

**播放页该是 Tab 还是 push？**

| 方案 | 好处 | 坏处 |
|---|---|---|
| 保持 Tab（现状，用户指定） | 底部一格，随时可去 | 从设备页点进去后"回不去"，且与 Tab 语义冲突 |
| 改成 push（Spotify 那样） | 返回语义自然，符合大厂 | 底部少一格，用户之前明确要保留 |

**折中方案**：播放格保留，但从设备页点设备时**不跳 Tab**，
而是 push 一个"设备控制面板"（现在 `Settings` 就是干这个的）。
这样"点设备 → 看这台设备在放什么 → 返回设备页"链路闭合，
而底部「播放」格留给"当前正在播的那一首"。

---

## 八、结论

1. 现在的 5 个 Tab 划分**是对的**（`docs/93` 已对齐大厂），不用再动
2. 问题全在**层级模型**：单层 `sub` + 写死的返回 + 反标准的返回键
3. 两个 P1 是**bug 级**，应该先修，不用等大重构
4. 大的重构（每 Tab 一个栈）收益明确但代价大，建议**单独一轮**
