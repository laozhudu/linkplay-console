## 零、结论

**能做，而且码库有 CC0 的完整来源（30 万条按键）。但有一个前提被 docs/49 搞错了，必须先纠正。**

| 问题 | 答案 |
|---|---|
| 有成熟码库吗 | **有，而且许可干净**：`Lucaslhm/Flipper-IRDB` **CC0-1.0**，8,901 个文件 / **301,915 条按键** / 47 类设备 |
| 手机能发吗 | 能。`ConsumerIrManager.transmit(freq, int[])`，API 19+，`TRANSMIT_IR` 是普通权限，无需运行时授权 |
| 手机能「学码」吗 | **不能。** Android 没有任何公开的红外接收 API。docs/49 说的「添加设备时录码」在纯手机上**做不到** |
| 该开模块吗 | 按现有三条判据**不该**（纯 JVM、无第三方依赖）。但**体积**这条让它必须单独放 —— 建议加第四条判据 |
| 值得做吗 | 中等。码库不是瓶颈，**「在 30 万条里找到你家那台」才是** |

## 一、先纠正 docs/49 的一个前提错误

`docs/49` 第 417 行写：

> 不做通用红外码库 | 几千个品牌几十万条码，只用得上自家那几台。**做「添加设备时录码」更实际**

**「录码」在手机上不可行。** 理由：

- `ConsumerIrManager` 只有三个方法：`hasIrEmitter()` / `getCarrierFrequencies()` / `transmit(int, int[])`。**全是发送，没有接收**
- AOSP 没有公开的红外接收 API。部分厂商 ROM 有隐藏实现，第三方 App 用不了
- 小米「万能遥控」里的学习功能走的是厂商私有实现，不是公开 API（未在真机上验证其原理，仅从「AOSP 无接收 API」推断）

**推论**：码库不是「可选方案之一」，是**唯一方案**。要么内置码库，要么这个功能不成立。

（例外：USB 学习型红外棒。`iodn/android-ir-blaster` 支持这类硬件，能真学码 —— 但那要外接设备，不是手机自带能力。）

## 二、码库：Flipper-IRDB 实测（真拉下来统计的，不是看 README）

`Lucaslhm/Flipper-IRDB`，**CC0-1.0**（公有领域，可自由使用、可商用、无需署名），4,462★，2026-04 最后推。

我把它整包拉下来（17MB tar.gz，解开 112MB）跑了精确统计：

```
.ir 文件      8,901
总大小        62.0 MB
按键条目      301,915
类别          47
```

**格式两种，决定实现难度：**

```ini
# ① parsed —— 只给协议参数，要自己算时序
name: POWER
type: parsed
protocol: NEC
address: 20 00 00 00
command: 02 00 00 00

# ② raw —— 直接给微秒时序，可以直接喂 ConsumerIrManager
name: Fan_2
type: raw
frequency: 38000
duty_cycle: 0.330000
data: 8983 3497 180 797 563 567 570 560 ...
```

| 类型 | 条目数 | 占比 | 我们还要做什么 |
|---|---:|---:|---|
| `parsed` | 170,475 | **56%** | 要写协议编码器 |
| `raw` | 131,442 | 44% | 直接发，零加工 |

**协议只有 13 种**（全量统计，不是抽样）：

```
NECext 144,290   NEC 9,599   RC5 7,860   Samsung32 2,451   Kaseikyo 1,639
SIRC 1,068   SIRC20 1,048   RC6 908   SIRC15 815   RCA 279
RC5X 212   Pioneer 180   NEC42 124
```

前两种占 90%。**13 个编码器 ≈ 300 行 Kotlin，全部是公开规范，没有算法难题。**

### 体积是关键约束

按类别统计体积：

| 类别 | 体积 | 文件数 |
|---|---:|---:|
| **`_Converted_`** | **54.8 MB** | 6,944 |
| ACs（空调） | 1.4 MB | 158 |
| TVs（电视） | 1.2 MB | 397 |
| Fans / LED / 投影 / 功放 / 机顶盒 / 回音壁… | 各 0.2–0.5 MB | 合计 ~500 |

- `_Converted_` 占 **88% 体积**，是脚本从 irplus/Pronto 批量转换来的，文件头自己都写着
  「NOTE: The flipper does NOT cope with this many entries!」
- **家用核心 10 类（电视/空调/机顶盒/回音壁/投影/DVD/蓝光/功放/风扇）= 1,180 文件 / 4.8 MB**

对照：现在 debug APK 是 **19MB**。全量码库塞进去会翻三倍，不可接受；
**核心 10 类 4.8MB（压缩后约 1.5MB）完全可以内置**，`_Converted_` 走按需下载。

## 三、手机端：API 现状

```java
ConsumerIrManager ir = (ConsumerIrManager) getSystemService(CONSUMER_IR_SERVICE);
if (ir.hasIrEmitter()) {
    ir.transmit(38000, new int[]{9000, 4500, 560, 560, ...});   // 单位微秒，同步阻塞
}
```

- **API 19+**，`android.permission.TRANSMIT_IR` 是 **normal 权限**（装的时候就有了，不用弹窗）
- 系统特性标记 `FEATURE_CONSUMER_IR`，用 `hasIrEmitter()` 判断
- `getCarrierFrequencies()` 返回支持的载波范围（多数是 30–56kHz）
- **`transmit` 是同步的**，长序列会阻塞，必须放后台线程
- 官方文档当前**没有** deprecation 标记（我拉的是最新在线文档）

**哪些手机还有红外（2026 年现状，国产机为主）**：

| 有 | 没有 |
|---|---|
| 小米/红米绝大多数（11 Ultra 例外） | 苹果全系 |
| 华为 P/Mate 部分、荣耀 Magic 系列 | 三星旗舰 |
| vivo X/iQOO 多数、OPPO Find/Reno 部分、一加数字系列 | vivo S 系列（轻薄机型砍了） |

所以**这个功能必须先检测、没有就完全不渲染入口**（docs/49 已经这么定了，正确）。

### 关于 Termux-IRBlaster 的 MIT 编码器

它 `generate_raw_timings()` 只有 80 行，覆盖 NEC/NECext/Samsung32/SIRC/SIRC15/SIRC20/RC5/RC5X/RC6/NEC42/Kaseikyo/RCA。
**许可允许抄，但它有实质错误，不能照搬**：

- **RC5 写错了**：RC5 是曼彻斯特编码，半位 889µs，它按「889/889 或 889/1778」两段式生成，位序也反了
- **Kaseikyo 写错了**：真实帧是 48 位（厂商码 + 厂商校验 + 品类 + 功能 + 校验），它只拼了 36 位
- NEC 的 `NECext` 分支和 `NEC` 合并处理，扩展地址的字节序没区分

**判断理由**：RC5 是曼彻斯特编码（每个位 1.778ms 由两个 889µs 半位组成，0/1 靠相位区分），
它写成「889 + 889/1778」两段式；Kaseikyo 真实帧约 48 位（厂商码+校验+品类+数据+校验），它只拼 36 位。
**这两条是按规范推断，没有上机验证。**

**正确做法**：协议时序是公开规范（NEC 是 9ms+4.5ms 引导 + 560/1690 编码），按规范独立实现，
再用真机抓到的码验证 —— 不要抄这 80 行。

## 五、能不能做成模块：按现有判据其实是「不该开」

`docs/69` 定的三条判据（任一满足才开）：

| # | 判据 | 红外 |
|---|---|---|
| 1 | 拖进纯 JVM 装不下的依赖 | ❌ 解析+编码是纯 Kotlin，`ConsumerIrManager` 调用只有 40 行 |
| 2 | 有第二个消费者 | ❌ 目前只有声控台 |
| 3 | 能独立发版且不依赖项目类型 | ⚠️ 勉强算（红外码库对别的项目有用） |

**三条都不硬。** 按判据它应该把解析器和编码器塞进 `core-protocol`，发射器塞进 `app`。

**但有个新约束让这条路走不通：体积。**

`core-protocol` 是零依赖、要 `maven-publish` 的纯 JVM 底座。往里塞 **4.8MB 码库资源**，
等于让任何引用这个库的项目都背上 4.8MB —— 这比拖一个第三方依赖更糟。

### 建议加第四条判据

> **4. 带大体积资源（>1MB 的数据文件）** —— 因为资源会跟着 jar 一起被消费方继承，无法剥离。

按这条，`core-ir` 应该开模块。切法：

```
core-ir（★新建，纯 JVM，零运行时依赖）
  ir/FlipperIrParser.kt      解析 .ir 文件（两种 type）
  ir/IrProtocol.kt          13 个协议的 timing 编码器
  ir/IrCode.kt              {name, category, brand, protocol|raw, freq}
  ir/IrLibrary.kt           码库索引（按类别/品牌/按键名查）
  assets/ir-core/…          家用核心 10 类 4.8MB（或按需下载）
    ↓ 被 app 引用，不反向依赖
app
  transport/IrTransport.kt   ConsumerIrManager 封装（~40 行，含 hasIrEmitter 检测）
```

**为什么编码器放纯 JVM 而不是 Android 模块**：13 个协议 + 解析器约 400 行，是唯一需要仔细测的部分。
放纯 JVM 就能像 `core-protocol` 那样跑单测（现在 613 个用例），不用真机。

## 六、真正的难点不是码库，是「找到你家那台」

30 万条按键听起来很全，但用户实际动作是：

> 「我要关空调」→ 哪台空调？什么品牌？什么型号？格力的哪个码集？

Flipper-IRDB 的组织是 `类别/品牌/型号.ir`，例如 `ACs/Admiral/Admiral_AC.ir`。
**同一品牌下可能有几十个型号文件，每个文件的按键集还不一样。** 这是体验的坑，不是技术的坑。

市面成熟 App 怎么解决：
- 小米万能遥控：先选品类 → 选品牌 → **逐个试「电源」键**，用户看到空调响了就点「有反应」
- 红外没有回执，**只能靠人眼确认**（这也是为什么 docs/49 把红外状态定义为「永远是不知道」）

所以第一版的合理范围：

| 做 | 不做 |
|---|---|
| 内置家用核心 10 类（1,180 文件） | 全量 30 万条 |
| 按「品类 → 品牌 → 型号」逐级浏览 | 全文搜索（搜「格力」出 200 个文件，没法用） |
| 常用键（电源/音量/方向/数字）单独置顶 | 试图映射成通用语义（「音量+」在每台电视码里名字都不一样） |
| 「这个键没反应？换下一个码集」 | 假装知道成功（红外无回执） |

## 七、结论与建议

### 值得做的部分

1. **码库不是问题**：CC0 的 30 万条摆在那，许可干净，格式直接对得上 `ConsumerIrManager`
2. **编码器是可控工作量**：13 个协议、约 400 行、纯 JVM 可单测
3. **体积可解**：核心 10 类 4.8MB 内置，`_Converted_` 按需下载

### 但优先级建议往后放

理由三条：

1. **前置条件太强**：手机没红外就整个功能不存在。而苹果/三星用户（包括你可能的下一台手机）完全没有
2. **边际价值低**：手机上已经有 Mi Remote（闭源但好用）、IR Blaster（开源、F-Droid、支持 Flipper 码库）。我们做的价值只在「和音箱遥控在同一个 App 里」
3. **体验难点在 UI 不在技术**：30 万条里找对的那条，是「逐个试」的笨办法，做不好比不做更烦人

### 如果要做，建议的最小版本

- **第一步**：只加 `hasIrEmitter()` 检测 + 一个「试发一条 NEC 电源码」的隐藏入口，**验证你自己的手机到底有没有红外**
- **第二步**：如果真有，先做**电视/机顶盒**（TVs 397 个文件 / 1.2MB），不做空调（空调码集最多最难匹配）
- **第三步**：再考虑扩到全量

**不要一上来就做「万能遥控」** —— 那是小米投了几百人年的东西，而且核心难点是「码集匹配的交互设计」，不是代码量。

## 九、一句话

**码库这一环已经从「没有」变成「有且免费」（CC0 / 30 万条），真正的门槛变成了「手机得有红外」和「怎么让人在 30 万条里找到对的那条」。技术不难，产品难。**
