## 三、边界怎么划的

### 3.1 会话恢复为什么是**一个**类，不是两个函数

`restoreLastDevice()` 和 `restoreLastQueue()` 原本是两个 private 函数，
在 `init` 里**按顺序**调两次。

看着很自然，但这是"调用方必须记得顺序"的设计：
- 只调设备 → 播放页空着
- 只调队列 → 不知道队列属于哪台
- 顺序反了 → 队列恢复时 `selectedIp` 还是 null，静默跳过

三种都不会报错，只会表现为"重开 App 列表是空的"。

所以搬出去时把它们合成一个 `restore()`，顺序写死在类里：

```kotlin
fun restore() {
    restoreLastDevice()
    restoreLastQueue()
}
```

**这是拆分时唯一改了行为的地方**——把"约定"变成"结构"。

### 3.2 恢复结果为什么要留状态

用户报得最多的是「重开 App 列表是空的」。这一句话对应三种原因：

| 原因 | 表现 | 修法 |
|---|---|---|
| 没有上次设备记录 | 列表空、播放页空 | 查存盘 |
| 记录对不上设备 | 同上 | 查 uuid/ip 变更 |
| 回到设备但设备上没有列表 | 有设备无列表 | 查设备侧队列 |
| 设备没有、本地也没有快照 | 有设备无列表 | 查本地快照写入 |

四种在界面上**完全一样**。所以 `SessionRestore` 把每一步的结果攒成
`RestoreStatus`，交给诊断页显示。

### 3.3 诊断为什么单独成类

不是为了行数，是因为这批代码**不改变任何状态**：
它只读 `ConsoleUiState`、`AppDiagnostics`、`CommandTrace`、`NavTrace`、`QueueBus`。

一个 1400 行的类里一半函数在改状态、一半在读状态，
"改这里会不会影响那里"就没法回答了。分出来以后：

- `ConsoleViewModel` = 改状态的地方
- `ConsoleDiagnostics` = 读状态的地方

依赖方向也干净了：诊断依赖宿主，宿主**不**依赖诊断（只调 `diagnostics.register()`）。

`register()` 由 `init` 调、不写在构造函数里：注册本身不读状态，
但"什么时候开始出现在诊断页"要在 init 里一眼可见。

## 四、诊断台这轮加了什么

新增第八段 **「启动恢复」**（`id=restore`，排在「设备」之后、「界面」之前）：

```
[启动恢复]
  设备=doss1（192.168.99.164）
  队列=122 首 · 第 1 首 · 来源=设备列表
  耗时=231ms
```

失败时：

```
[启动恢复]
  设备=未恢复（上次设备不在已保存列表（FF31...））
  队列=设备无列表，本地也没有快照
  耗时=0ms
```

严重度规则：

| 条件 | 级别 | 意思 |
|---|---|---|
| 一台设备都没保存 | INFO | 本来就没什么可恢复 |
| 有设备但回不到上次那台 | WARN | 存盘或 uuid 变了 |
| 回到设备但列表没回来 | WARN | 设备侧空 + 本地快照也空 |
| 都成功 | INFO | — |

**这是铁律一要求的"成功也记"**：没有这条，"没恢复"和"根本没执行"分不开——
用户说"列表空了"，我原来只能反问他"你上次听的是哪台"。

## 五、为什么 app 模块总行数是**变大**的

15224 → 15451（+227）。原因：

1. 三处新写的类注释（为什么要拆、边界怎么划）—— 这部分是有意留的
2. `SessionRestore` 的 `RestoreStatus` 状态机（原来没有）
3. 新的「启动恢复」诊断段（原来没有）

**拆分的目标不是"行数变少"**，是"改一块不用先读懂 1400 行"。
如果每轮拆分都靠删注释来让数字好看，下一批人接手时就没有"为什么这么划"的依据了。
行数下降只是副产品。

真正该看的指标是**最大文件的行数**：1409 → 1183。

新增的 5 个用例（`session/SessionRestoreTest.kt`）锁的是设备恢复的四种判定：

1. 按 uuid 找回 → 选中 ip/uuid/location 三项都对
2. 记录是 `ip:` 键 → 也能找回
3. 没有记录 → 给出原因，不静默
4. 记录对不上 → 给出原因
5. 上一次成功、这一次失败 → 状态反映这一次（不残留）

替身 `FakeHost` 的其余方法一律**抛异常**而不是返回默认值：
将来有人让恢复逻辑顺手发个命令，会在测试里立刻炸掉。

### 未验证（必须靠真机）

- 「启动恢复」段在真机上的实际输出 —— 单测碰不到设备往返
- 队列恢复走了 `BrowseQueue` / `getPlayerStatus` 两条真实网络路径，**没有**被单测覆盖
- 合并后 APK 覆盖安装后能否正常启动（版本号自动 = 提交数 = 0.9.65）

**说清楚**：`restoreLastDevice` 的四种分支有单测，
`restoreLastQueue` **一行都没测到**（它要设备在网里）。这部分靠诊断报告确认。
